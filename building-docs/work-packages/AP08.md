# 0. Zweck und Rolle von AP08

AP08 macht aus der bisherigen mehrsprachigen Relaunch-Struktur einen belastbaren, technisch konsistenten und vollständig prüfbaren 10-Sprachen-Betriebszustand.

AP08 ist kein reines Übersetzungspaket.

Es besitzt sechs miteinander gekoppelte Aufgabenfelder:

1. einen gemeinsamen Server-/Client-i18n-Kern,
2. die technische Lokalisierbarkeit bisher hartcodierter Seiten,
3. vollständige Namespace- und Key-Parität,
4. konsistente locale-aware Navigation und Routing-Semantik,
5. lokalisierte System-, Formular- und Mailtexte,
6. ehrliche Behandlung sprachabhängiger Assets.

Das Arbeitspaket beseitigt insbesondere die aktuelle Situation, in der Teile der Website zwar zehn Locale-Präfixe kennen, der reale Seiteninhalt aber nur in einer oder zwei Sprachen gepflegt ist.

AP08 darf keinen Zustand erzeugen, in dem eine Seite technisch unter zehn Locale-URLs erreichbar ist, aber still Englisch oder Deutsch als regulären Inhalt ausliefert und dies als vollständige Lokalisierung ausgibt.

Der zentrale Qualitätsgrundsatz lautet deshalb:

> **Fallback ist Fehlerbehandlung, nicht Content-Strategie.**

Nach AP08 müssen fehlende Übersetzungen automatisiert sichtbar werden. Ein produktiver Relaunch-Bereich darf nicht still auf eine andere Sprache zurückfallen, wenn laut Scope eine vollständige 10-Sprachen-Fassung erwartet wird.

# 6. AP08 i18n Contract

AP08 stellt einen verbindlichen i18n-Vertrag her.

## 6.1 Sprache aus URL

Die URL ist die einzige primäre Sprachquelle für Seitenrendering.

Nicht zulässig als konkurrierende Quelle:

- Browser-Language als persistente Seitenwahrheit,
- `localStorage` als Routing-Wahrheit,
- Cookie als primäre Seitensprache,
- Zustand nur im React Context ohne URL-Abbildung.

Browser-Präferenz darf höchstens zur initialen explizit zulässigen Navigation verwendet werden, sofern Scope/Server-Vertrag dies vorsieht.

Nach Navigation gilt die URL.

## 6.2 Supported Languages

Es muss genau eine semantisch konsistente Liste geben:

`de,en,pl,fr,it,es,pt,da,nl,cs`

Wenn Server und Client technisch noch getrennte Spiegel benötigen, müssen Guards Gleichheit beweisen.

AP10 darf später die zentrale Route-Wahrheit weiter konsolidieren.

## 6.3 Default Language

Default:

`de`

## 6.4 Fallback Language

Fallback:

`en`

aber ausschließlich als defensiver Fehlerpfad.

Produktive Vollständigkeit wird nicht dadurch erfüllt, dass ein fehlender Key auf Englisch sichtbar wird.

## 6.5 Namespace Contract

Jeder produktiv verwendete Namespace muss:

- registriert,
- für alle zehn Sprachen vorhanden,
- syntaktisch gültig,
- key-paritätisch,
- im Guard enthalten

sein.

Legacy-/Backlog-Namespaces werden bewusst klassifiziert und nicht still als produktiv behandelt.

## 6.6 Missing-Key Contract

Ein fehlender produktiver Key ist ein Quality-Gate-Fehler.

Nicht zulässig:

- Key-String im UI,
- stiller EN-Mix ohne Fehlerklassifikation,
- absichtliches Kopieren englischer Texte in andere Locale-Dateien als „Übersetzung“.

## 6.7 Language Fallback Notice

`LanguageFallbackNotice` ist nur für echte Fehler-/Recovery-Fälle zulässig.

Nicht als reguläre Anzeige für dauerhaft unübersetzten Content.

## 6.8 HTML `lang`

`<html lang>` bzw. SSR-/Client-Semantik muss mit der tatsächlich dargestellten Sprache übereinstimmen.

Kein Zustand:

`lang="pl"` + englischer Body als regulärer Betrieb.

## 6.9 Locale Formatting

Datum, Zahl, Währung und Preis werden über locale-aware Formatierung ausgegeben.

Nicht:

- hartcodiertes `toLocaleString('de-DE')` in anderssprachigen Seiten,
- manuell zusammengesetzte Dezimal-/Währungsformate,
- feste Datumsreihenfolge in UI-Strings.

## 6.10 Generated i18n Contract

AP08 PT08.3 soll einen maschinell erzeugbaren Bericht bereitstellen, vorzugsweise:

`building-docs/I18N-CONTRACT.md`

Dieser Bericht ist generierte Evidenz, nicht eine zweite manuell gepflegte i18n-Wahrheit.

Er enthält mindestens:

- Supported Languages,
- produktive Namespaces,
- Namespace-Dateiabdeckung,
- Key-Paritätsstatus,
- Fallback-Konvention,
- bewusst ausgeschlossene Legacy-Namespaces,
- Asset-Asymmetrien,
- offene ownergebundene i18n-Integrationen.

- Fallback Namespace,

## 7.4 URL als einzige Sprachquelle

Prüfe alle Wege, die aktuelle Sprache bestimmen.

Ziel:

- SSR liest Locale aus Request-URL,
- Client liest Locale aus Route,
- Hydration startet in derselben Sprache,
- Sprachwechsel navigiert auf neue Locale-URL,

## 7.5 SSR-Fallback

Serverseitig benötigte Namespaces werden deterministisch geladen.

Fallback muss:

- SSR nicht crashen lassen,
- Hydration nicht divergieren lassen,
- fehlende Übersetzung aber messbar machen.

## 7.6 Namespace-Registrierung

Inventarisiere:

- registrierte Namespaces,
- tatsächlich verwendete Namespaces,
- vorhandene Locale-Dateien,
- Legacy-/Backlog-Dateien.

Konsolidiere produktive Namespace-Liste.

Keine Case-Study-/Shop-Reaktivierung.

## 7.7 `lang`-Attribut

Prüfe SSR und Client.

Für jede unterstützte Locale muss das Dokument die korrekte Sprache ausweisen.

## 7.8 FallbackNotice

Prüfe heutige `translationStatus`-Semantik.

`FallbackNotice` darf nur erscheinen, wenn tatsächlich ein defensiver Fallback genutzt wird.

Nach vollständiger AP08-Lokalisierung ist regulär:

`FallbackNotice count = 0`

auf den zehn Kern-Locale-Smokes.

## 7.9 Tests

Mindestens:

- Supported Languages exakt ×10,
- shared config browser-/node-neutral,
- Server/Client Locale-Parität,
- URL-Locale gewinnt,
- SSR-Initialsprache,
- Hydration-Parität,
- `lang` korrekt,
- Namespace-Laden,
- Fallback nur defensiv,
- unbekannte Locale sicher behandelt.

## 7.10 Akzeptanzkriterien PT08.1

PASS nur wenn:

- gemeinsame i18n-Konfiguration konsistent,
- URL einzige primäre Sprachquelle,
- SSR und Client stimmen überein,
- Namespace-Registrierung bewusst klassifiziert,
- `lang` korrekt,
- FallbackNotice nicht als Content-Strategie missbraucht,
- keine AP09/AP10-Großarbeit vorgezogen,
- relevante Tests grün.

# 9. PT08.3 — Namespace- und Key-Parität

## 9.1 Ziel

Alle produktiven Namespaces und spezialisierten Content-Modelle besitzen echte zehnsprachige Vollständigkeit und maschinell beweisbare Parität.

## 9.2 Produktive Namespace-Inventur

Ermittle aktuell:

- welche Namespaces registriert sind,
- welche Namespaces produktiv geladen werden,

- welche Locale-Dateien fehlen,
- welche Keys fehlen,
- welche Dateien syntaktisch ungültig sind.

## 9.3 Epigenetics × 10

`epigenetics` muss in zehn Sprachen vollständig sein.

Dabei:

- keine 8× englischen Kopien als scheinbare Übersetzung,
- Fachclaims nicht frei neu formulieren,
- AP15-fachliche Deferred Gates respektieren,
- bereits freigegebene Ausgangstexte fachlich treu lokalisieren.

Wenn ein konkreter medizinischer Text keine freigegebene Ausgangsfassung besitzt:

nicht erfinden.

Stattdessen ownergebunden dokumentieren.

Ein großflächiger `epigenetics`-EN-Fallback ist jedoch kein AP08-PASS-Zustand.

## 9.4 Befund-Inhalte × 10

Bestehende Lazy-Loading-/Chunk-Grenze erhalten.

`Befund { de, en, pl, fr, it, es, pt, da, nl, cs }`

oder eine äquivalent saubere lazy geladene Struktur.

## 9.5 Fehlende `befund.*` Keys

Alle produktiv referenzierten Befund-UI-Keys müssen über zehn Locales vorhanden sein.

## 9.6 Fehlende `services.*.seo.*` Keys

## 9.7 Guard G4

- jede unterstützte Sprache vorhanden,
- jeder produktive Namespace für jede Sprache vorhanden,
- JSON parsebar,
- gleiche Key-Struktur gegen kanonische Referenz,
- keine unbekannten produktiven Namespace-Dateien,

- keine leeren Pflichtwerte,

## 9.9 Keine stillen Sprachmischungen

Ausnahmen:

- Produktname,
- Eigennamen,

Diese Ausnahmen nicht global als Freifahrtschein formulieren.

## 9.10 I18N-CONTRACT

Generiere/aktualisiere:

`building-docs/I18N-CONTRACT.md`

als Guard-Evidenz.

Keine manuelle zweite Wahrheit.

## 9.11 Tests

Mindestens:

- produktive Namespace-Liste,
- 10/10 Locale-Dateien,
- Key-Parität,
- Befunde 10/10,
- Epigenetics 10/10,
- service SEO keys,
- JSON parse,

- no silent fallback in smoke routes,
- CI guard executes.

## 9.12 Akzeptanzkriterien PT08.3

# 10. PT08.4 — Sprachwechsel und Routen

## 10.1 Ziel

Ein Sprachwechsel hält Nutzer auf derselben logischen Seite, sofern diese Seite in der Zielsprache laut Relaunch-Scope unterstützt wird.

- Epigenetics Vertiefungen,
- Musterbefunde,
- Downloads,
- Events,

- Spezialseiten.

`/de/diagnostics/foo` → `/fr/diagnostics/foo`

Nicht:

`/de/diagnostics/foo` → `/fr/`

- `/s3_leitlinie`

Keine Hydration-Regression erzeugen.

## 10.5 URL bleibt Wahrheit

Language Switch darf keinen konkurrierenden unsichtbaren Locale-State erzeugen.

## 10.6 Canonical / hreflang Synchronität

AP08 prüft, dass bestehende Canonical-/hreflang-Ausgabe nicht der neuen Routing-Wahrheit widerspricht.

Aber:

- keine neue SEOHead-Plattform,
- keine Sitemap-Plattform,
- keine Structured-Data-Neuarchitektur.

AP09 übernimmt die finale SEO-Konsolidierung.

## 10.7 `x-default`

`x-default` bleibt konsistent mit dem bestätigten Default-Markt:

`de`

Sofern der bestehende SEO-Vertrag `x-default` bereits ausgibt, darf AP08 ihn nicht versehentlich auf `en` verschieben.

## 10.8 Nicht vorhandene Inhalte

Nach AP08 sollten Relaunch-Kerninhalte x10 verfügbar sein.

Falls eine konkrete fachlich blockierte Seite tatsächlich nicht in einer Zielsprache veröffentlicht werden darf:

- keine Fake-Locale-Route mit falscher Sprache,
- keine hreflang-Behauptung,
- ownergebundene Ausnahme dokumentieren.

## 10.9 Tests

Matrix mindestens:

10 Sprachen × repräsentative Routentypen.

- HTTP 200,

- korrektes `lang`,

- keine Redirect-Loops,
- keine Hydration-Mismatches.

## 10.10 Akzeptanzkriterien PT08.4

# 15. Risikoregister

## R08-01 — Silent English Fallback

**Risiko:** Paritätscheck ist formal grün, weil englische Texte in andere Locale-Dateien kopiert wurden.  
**Mitigation:** sprachliche Plausibilitätsprüfung + Stichproben + heuristische Guard-Prüfung.

## R08-02 — SSR/Hydration Locale Drift

**Risiko:** Server und Client bestimmen unterschiedliche Sprache.  
**Mitigation:** URL als einzige Quelle + SSR/Client Testmatrix.

## R08-03 — Namespace Drift

**Risiko:** Datei existiert, ist aber nicht registriert oder nie geladen.  
**Mitigation:** Guard vergleicht Registrierung, Verwendung und Dateien.

## R08-04 — Consumer Migration Explosion

**Risiko:** 2884+ Zeilen werden nebenbei redesigniert.  
**Mitigation:** AP08 nur i18n-Struktur + vorhandene Copy; AP21 bleibt Produkt-Owner.

## R08-05 — Medical Translation Drift

**Risiko:** Fachinhalt wird beim Übersetzen semantisch verändert.  
**Mitigation:** Ausgangsfassung beibehalten; ungeklärte Claims nicht neu erfinden; fachliche Owner-Gates erhalten.

## R08-06 — Befund Bundle Regression

**Risiko:** zehn Sprachen vergrößern globales Bundle stark.  
**Mitigation:** vorhandene lazy Content-Grenze erhalten.

## R08-07 — Redirect Loop

**Risiko:** Abbau von DE-/EN-Sonderredirects erzeugt Schleifen.  
**Mitigation:** HTTP/route matrix ×10.

## R08-08 — SEO Ownership Collision

**Risiko:** PT08.4 baut vor AP09 eine zweite Canonical/hreflang-Plattform.  
**Mitigation:** nur Compatibility-Fix; Plattform bleibt AP09.

## R08-09 — Future Mail False Ready

**Risiko:** Übersetzungskeys werden als funktionierende Mailzustellung ausgegeben.  
**Mitigation:** Runtime Exists und Translation Contract separat reporten.

## R08-10 — Asset Fabrication
