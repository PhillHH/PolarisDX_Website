# 0. Zweck und Rolle von AP13

AP13 baut die neun diagnostischen Service-Detailseiten zu einem konsistenten, skalierbaren und conversion-fähigen Seitensystem aus.

Der Diagnostics Hub aus AP12 beantwortet die Frage:

> Welche diagnostischen Leistungsbereiche bietet PolarisDX und welcher Bereich ist für mich relevant?

AP13 beantwortet auf den jeweiligen Detailseiten:

> Was ist dieser Service, für wen ist er relevant, welche diagnostischen Fragestellungen und Parameter werden abgedeckt, wie funktioniert der Workflow, welche belastbaren Proof-/FAQ-Inhalte gibt es und wie geht es zur Anfrage weiter?

AP13 ist damit der Übergang von der Hub-Navigation zur fachlich differenzierten Service Journey.

Das Arbeitspaket muss gleichzeitig zwei Ziele erfüllen:

1. **Konsistenz:** Alle neun Detailseiten folgen einem gemeinsamen strukturellen und technischen System.
2. **Differenzierung:** Jede Service Family besitzt echte eigene Inhalte, relevante Use Cases, Parameter-/Workflow-Einordnung und einen passenden Conversion-Pfad.

Keine Seite darf nur eine duplizierte Template-Kopie mit ausgetauschtem Titel sein.

# 10. Gemeinsamer Service Content Contract

## 10.1 Content muss differenziert sein

Jede Service Family besitzt eigenständige fachliche Aussage.

Nicht zulässig:

- identischer Hero mit nur ausgetauschtem Service-Namen
- identische Use Cases über alle Services
- identische FAQ über alle Services
- identische Markerlisten ohne fachliche Evidenz
- generische „innovative Diagnostik“-Copy als Ersatz für echte Einordnung

## 10.2 Problem-/Nutzen-Logik

Jede Seite soll verständlich machen:

- welches Problem / welcher professionelle Bedarf adressiert wird
- für welchen Kontext die Leistung relevant ist
- welchen Workflow-/Informationsnutzen sie bietet

Keine medizinische Wirkgarantie.

## 10.3 Use Cases

Use Cases müssen aus realem Produkt-/Servicekontext ableitbar sein.

Keine erfundenen Branchen-/Praxisfälle nur zur Seitenfüllung.

## 10.4 Parameter / Marker

Nur reale, belegte Tests / Parameter / Marker verwenden.

Keine Liste aus Vermutungen.

Wenn Repository-/freigegebene Content-Evidenz nicht genügt:

- keine erfundene Vollständigkeit
- offen ownergebunden dokumentieren
- Seite im sicheren Zustand ausliefern

## 10.5 Workflow

Workflow muss tatsächliche aktuelle Leistungs-/Produktlogik spiegeln.

Keine zukünftige Backend-/CRM-/Produktfunktion als bereits verfügbar darstellen.

## 10.6 Proof

Zulässig nur mit realer Evidenz:

- freigegebene Kennzahlen
- real vorhandene Partner-/Kundenbezüge
- bestehende Produkt-/Prozessmerkmale
- real vorhandene Literatur-/Content-Verweise

Keine Fake-Proof-Elemente.

## 10.7 FAQ

FAQ nur mit realen, sichtbaren Fragen/Antworten.

Keine SEO-only versteckten FAQs.

## 10.8 Related Content

Nur reale veröffentlichte Inhalte:

- Articles
- Resources
- IglooPro
- Epigenetics
- Specialty Pages
- Diagnostics Hub

Keine Draft-/Dead-/Legacy-Links.
