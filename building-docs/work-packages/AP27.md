# 0. Zweck

AP27 macht aus den bis AP26 aufgebauten Produkt-, Routing-, SEO-, i18n-, Lead-, Consent-, Accessibility-, Performance- und Security-Verträgen ein dauerhaft ausführbares Qualitätsnetz.

AP27 besitzt insbesondere:

- Unit-/Component-Teststrategie für zentrale fachliche und technische Verträge
- Integrationstests für SSR, HTTP-Semantik, SEO, Lead-Persistenz, Queue/Retry und geschützte Assets
- E2E-Kernjourneys über reale Browserpfade

- Visual Regression für visuell sensible Kernflächen
- Accessibility-Regression als CI-Gate, ohne AP24 zu duplizieren
- Token-/i18n-/Meta-/Design-System-Guards
- Aggregation der zwölf Launch-Gates aus dem Master-Scope
- CI-Trigger, Branch-Reichweite, Failure-Semantik und reproduzierbare lokale Kommandos
- `QUALITY-GATES.md`, `TESTING-CONTRACT.md` und `CI-CONTRACT.md` als ausführbare Wahrheit, sofern bereits vorhanden konsolidiert statt dupliziert

AP27 darf keinen PASS erzeugen, indem es Tests abschwächt, fehlerhafte Baselines akzeptiert oder reale Regressionen mit pauschalen Excludes versteckt.

# 3. FAST-DELTA V2

FAST-DELTA V2 ist verbindlich.

## 3.1 Grundregeln

1. PT27.1 macht die einmalige bounded Test-/Gate-Discovery und erzeugt den strukturierten AP27-Handoff.
2. PT27.2–PT27.5 konsumieren primär den direkten Vorgänger-Handoff.
3. Keine breite Repository-Rediscovery ohne konkretes Drift-Signal.
4. Nur Primary Write Set, direkte Imports, task-owned Tests und konkret fehlerrelevante Dateien öffnen.
5. Bereits bewiesene fachliche Invarianten nicht durch vollständige Feature-Reaudits duplizieren.
6. PT27.1–PT27.5 testen primär den jeweils eigenen Delta plus unmittelbare Verträge.
7. PT27.6 ist der breite Gate-/CI-Aggregationslauf.
8. AP27-CLOSURE reverifiziert unabhängig und breit und vertraut keinem PT-PASS blind.
9. Ein späterer PT repariert keinen fehlgeschlagenen Vorgänger heimlich.
10. Keine globale Testschwächung, um bestehende Fehler grün zu bekommen.
11. Keine Snapshot-Neubaseline ohne nachvollziehbare visuelle Begründung.
12. Flaky Tests werden nicht durch großzügige Retries maskiert; Ursache oder deterministische Stabilisierung ist zu dokumentieren.
13. Testdaten bleiben synthetisch; keine echten Kundendaten, Credentials oder produktiven Side Effects.
14. Preview/Staging darf keine realen CRM-/Mail-/Shop-/Analytics-Side-Effects auslösen, soweit der jeweilige Test nicht explizit auf eine isolierte Testintegration zielt.
15. `.github/workflows/ci.yml` ist gemeinsamer Hotspot. Bestehende AP24/AP25/AP26-Schritte nicht überschreiben, sondern koordiniert konsolidieren.
16. AP28 nicht als Nebeneffekt implementieren. AP27 darf Deployment-Smokes konsumieren, aber nicht den finalen Compose-/Backup-/Rollback-Betrieb bauen.

## 3.2 Testpyramiden-Prinzip

Jeder Vertrag soll auf der **kleinsten sinnvollen Teststufe** bewiesen werden:

- Pure Domainlogik → Unit
- Komponenteninteraktion / Semantik → Component
- mehrere Server-/Repository-Grenzen → Integration
- Browser + Netzwerk + Routing + echte User Journey → E2E
- Layout-/CSS-Veränderung → Visual Regression
- systemweite Konfiguration / Lieferkette → CI/Guard

Kein Browser-E2E für eine reine Stringfunktion, kein Unit-Test als Ersatz für echte Network-Evidence.

## 3.3 Flake-Policy

Ein Test ist nicht „grün“, wenn er nur mit hoher Retry-Zahl gelegentlich besteht.

Erlaubt:

- technisch begründete, kleine Retry-Zahl für bekannte Browser-/Netzwerk-Races
- deterministische Waits auf echte Zustände
- explizite Clock-/Date-/Animation-Stabilisierung

Nicht erlaubt:

- `sleep` als Standardstrategie
- pauschales `retries: 5+`
- Snapshot-Akzeptanz nach Flake ohne Ursachenanalyse
- `test.skip`/`fixme` auf Launch-Gates ohne ownergebundenen Blocker

# 4. Harte AP27-Regeln

- Repository Truth gewinnt gegenüber alten Prompt-Literalen.
- Tests beweisen reale Verträge; sie dürfen den Produktcode nicht nur an Testannahmen anpassen.
- Keine PII, echte Kundendaten oder produktiven Credentials in Fixtures/Snapshots/Logs.
- Keine produktiven CRM-/Mail-/Analytics-Side-Effects aus CI.
- GTM-/GA4-E2E muss Network-Evidence verwenden; DOM- oder dataLayer-only ist für das Pre-Consent-Gate nicht ausreichend.
- Vor Consent müssen Analytics-/Marketing-Provider-Requests = 0 bleiben.
- Kein Pre-Consent-Buffer und kein Replay nach späterem Grant.
- Conversion-Events erst nach persistiertem, wahrheitsgemäßem Business-State.
- Route-Tests müssen echte HTTP-Statuscodes prüfen, nicht nur sichtbaren 404-Text.
- Redirect-Tests prüfen Status, Ziel und Hop-Anzahl.
- Canonical/hreflang/Sitemap-Tests lesen die tatsächlich ausgelieferte SSR-/XML-Wahrheit.
- `lastmod` darf nicht nur syntaktisch existieren; es muss dem aktuellen SEO-Vertrag entsprechen.
- i18n-Guard umfasst alle launchrelevanten Namespaces, nicht nur Home.
- x10 heißt exakt `de,en,pl,fr,it,es,pt,da,nl,cs`.
- Default/x-default bleibt `de`.
- Visual Regression darf nicht die alternative `redesign/preview`-Art-Direction übernehmen; nur QA-/Snapshot-Technik ist importierbar.
- Light/Sales-Machine bleibt visuelle Wahrheit.
- Visual Baselines sind versioniert und absichtlich aktualisiert.
- Baseline-Update ohne erklärten Produkt-/Design-Delta ist FAIL.
- axe-Tests ergänzen AP24; sie ersetzen keinen manuellen Screenreader-/Keyboard-Nachweis.
- Accessibility serious/critical = 0 im definierten Scope.
- Design-Token-Guard bleibt aktiv und darf nicht durch breite Excludes entwertet werden.
- Meta-Description-Guard läuft in CI.
- Changelog-Gate greift nur für relevante Design-System-/visuelle Baseline-Änderungen, nicht für jede beliebige Codeänderung.
- Unit-, Integration-, E2E-, Visual- und CI-Gates müssen lokal reproduzierbare Kommandos besitzen.
- CI muss auf der tatsächlichen Relaunch-Linie / relevanten PR-Zielen greifen, nicht ausschließlich auf einem unberührten `main`.
- Node-/Package-Manager-Version in CI muss der aktuellen Toolchain-Wahrheit entsprechen oder Drift explizit verhindern.
- `lint`, `format`, `typecheck`, `build` und relevante Tests dürfen nicht als „allowed failure“ laufen, wenn sie Launch-Gates sind.
- Vorbestehende rote Baselines dürfen nicht pauschal ignoriert werden; Owner/Scope/Status müssen exakt dokumentiert sein.
- Kein „PASS“, wenn das Kommando nie in CI ausgeführt wird.
- Kein „PASS“, wenn der Test nur gegen alte `dist`-Artefakte läuft.
- Testserver müssen den aktuellen Build/HEAD belegen.
- Zeit-/Eventdaten werden für deterministische Tests kontrolliert, ohne reale Produktlogik zu verfälschen.
- Protected Asset-/Entitlement-Tests dürfen keine echten Tokens in Logs/Snapshots schreiben.
- Security-Tests aus AP26 bleiben Security-eigen; AP27 aggregiert nur die Gate-Reichweite.
- Performance-Budgets aus AP25 bleiben Performance-eigen; AP27 darf ihren CI-Status aggregieren, aber keine Schwellen erfinden.
- Shopify-only bleibt bindend: kein interner Purchase-Flow als AP27-DoD.
- AP28 bleibt NOT STARTED bis AP27-CLOSURE PASS in dieser seriellen Queue.

Die zentralen Relaunch-Verträge dort auf Unit-/Component-Ebene absichern, wo deterministische schnelle Tests den höchsten Hebel besitzen, und gleichzeitig die Testpyramide sowie aktuelle Coverage-Lücken belastbar dokumentieren.

## Scope

1. Route Registry und Route-Domainlogik.
2. SEOHead / Head-Helper.
3. i18n-Key-/Locale-Helper.
4. Lead-/Consent-Domainlogik.
5. CRM-/Queue-Adapter mit Test-Doubles.
6. zentrale UI-Patterns.
7. Testkonfiguration / eindeutige Scripts.
8. AP27-Testinventar und Handoff.

## Bounded Discovery

Einmalig erfassen:

- vorhandene Unit-/Component-Testdateien
- Test Runner / Config
- bekannte rote Baselines
- ungetestete zentrale Domainmodule
- aktuelle Guards und deren CI-Reichweite
- Node-/Toolchain-Version
- AP24/AP25/AP26-Handoffs
- bestehende `QUALITY-GATES.md`-/Testing-Dokumente

Keine erneute fachliche Vollprüfung aller Seiten.

## Route Registry

Mindestens beweisen:

- bekannte Route → korrekte Locale-/Slug-Auflösung
- unbekannte Route → nicht fälschlich bekannt
- Redirect-Mapping stabil
- Search/Sitemap/SSR benutzen dieselbe Registry oder Guard schlägt bei Drift an
- Consumer/Epigenetik/Resource/Legal-Segmente im erwarteten Modell

## SEOHead

Mindestens:

- Canonical
- hreflang ×10 + x-default
- noindex-Regel
- OG/Twitter zentrale Felder
- keine Preview-Domain
- 404/redirect Head nicht fälschlich indexierbar

## i18n Helper

Mindestens:

- exakte Locale-Liste
- default `de`
- Normalisierung
- Fallback nur gemäß aktuellem Vertrag
- fehlender Namespace/Key wird vom Guard erkannt

## Lead-/Consent-Domainlogik

- persist-before-handoff State Machine
- Idempotency-Key-/Replay-Entscheidung

# 9. PT27.2 — Integration Tests

## Ziel

Repository-, SSR-, Backend- und Persistenzgrenzen so testen, dass Cross-Layer-Regressionsfehler erkannt werden, ohne für alles einen Browser zu benötigen.

## Scope

1. SSR + Head.
2. HTTP 200/301/404.
3. Sitemap/hreflang.
4. Formular → Persistenz → Queue → CRM-Testadapter.
5. Retry/Recovery/Dead-Letter gemäß aktuellem Lead-Vertrag.
6. gated Asset-Entitlement.
7. Preview/`DRY_RUN`-/Side-Effect-Isolation.
8. Backend-/Server-Testkommando.

## SSR + Head

Beweisen:

- erster HTTP-Response enthält seitenbezogenen Head
- Canonical/hreflang im SSR
- lokalisierter Titel/Description
- 404/redirect Semantik stimmt mit Registry überein
- Client-Hydration ist nicht nötig, um zentrale SEO-Semantik zu erhalten

## HTTP

Mindestens:

- repräsentative 200-Routen
- locale-less redirect → erwarteter 301/Status
- `/services*` → echte 301 gemäß Route Contract
- echte unbekannte Route → 404
- unbekannter Content-Slug → 404

Assertions müssen `response.status()` / Location prüfen.

## Sitemap/hreflang

- XML parsebar
- alle erwarteten Route×Locale-Kombinationen
- keine Preview-Domain
- keine noindex-Routen, sofern Vertrag sie ausschließt
- hreflang Ziel-URLs erreichbar/kanonisch
- x-default `de`

## Lead Integration

Mit synthetischem Lead und Testadapter:

```text
request
→ server validation
→ persistence
→ outbox/queue state
→ adapter handoff
→ terminal/retry state
```

Prüfen:

- Persistenz zeitlich vor externem Handoff
- Journey/source/language/context
- Idempotency
- retryable failure
- unknown result behavior
- kein Verlust bei Providerfehler

## Gated Asset

- stabile Asset-ID
- Lead/Entitlement binding
- protected resolver
- realer Fixture-/Test-Assetzugriff
- invalid/wrong/expired/revoked negatives gemäß aktuellem Contract
- kein arbiträrer Dateipfad

## DRY_RUN / Preview Isolation

Wenn aktuelle Architektur `DRY_RUN` oder äquivalente Isolation besitzt:

- kein produktiver CRM-/Mail-Side-Effect
- State bleibt truth-safe
- Testadapter/No-Provider-State ehrlich

Kein künstlicher `DRY_RUN` nur für den Test erfinden, wenn aktuelle Architektur anders isoliert.

## Akzeptanz

- SSR/HTTP/SEO-Cross-Layer testbar
- Lead-Persistenz/Handoff testbar
- Retry/Recovery testbar
- gated Entitlement testbar
- Preview-Isolation testbar
- keine echten externen Provider
- exakter PT27.3-Handoff

# 14. AP27-CLOSURE

## Ziel

Unabhängig neu vermessen, ob AP27 tatsächlich ein belastbares, reproduzierbares und nicht künstlich grünes Quality-Gate-System hergestellt hat.

Closure vertraut keinem PT-Bericht blind.

## Start-Gate

Erforderlich:

- PT27.1 PASS
- PT27.2 PASS
- PT27.3 PASS
- PT27.4 PASS
- PT27.5 PASS
- PT27.6 PASS
- AP27 IN_PROGRESS
- AP28 NOT STARTED

Fehlt ein Vorgänger:

```text
AP27 CLOSURE RESULT
BLOCKED
Reason: BLOCKED_PREDECESSOR
```

STOP.

## Independent Reverification

Neu prüfen:

### Test Layering

- Unit/Component Coverage der kritischen Contracts
- Integration Layer
- E2E Kernjourneys
- Consent Network E2E
- Route/SEO Regression
- Visual/A11y

### CI Reachability

- aktueller Branch/PR-Scope
- alle harten Commands wirklich referenziert
- keine `continue-on-error`-Umgehung
- keine versteckten allowed failures
- CI-Konfiguration syntaktisch/semantisch plausibel

### Mutation/Negative Evidence

Mindestens stichprobenartig mutieren oder gezielt beweisen, dass folgende Fehler erkannt würden:

- Route-Registry Drift
- falscher 404-Status
- fehlender hreflang
- fehlender i18n-Key
- Pre-consent GTM Request
- fehlende Persistenz vor Handoff
- Public Bypass des Lead Magnets
- Design Token Drift
- Meta Description fehlt
- Visual Regression
- Accessibility serious/critical
- Claim-Rollback `<5 %>`

Mutation muss reversibel und working-tree-safe sein.

### Twelve Gate Audit

Für jedes der zwölf Gates:

- Owner
- Contract
- Test/Command
- CI Step
- Evidence
- Status

Ein Gate mit bewusst späterem AP28-Anteil bleibt ownergebunden, wenn die noch fehlende Funktion außerhalb AP27 liegt. AP27 kann trotzdem COMPLETE sein, wenn sein Auftrag — automatisierter oder eindeutig dokumentierter Nachweis — erfüllt ist und der Rest korrekt an den Owner gebunden ist.

## Closure PASS nur wenn

- AP27-eigene Tests/Gates grün
- keine fake/unused Guards
- CI-Reichweite real
- keine kritische Flake-Maskierung
- keine produktiven Side Effects
- keine Secret/PII-Artefakte
- Quality-Gates-Dokument current
- Testing-/CI-Contracts current
- zwölf Launch-Gates nachvollziehbar gemappt
- AP28 als nächster Owner klar

# 16. Risikoregister

## R27-01 — CI läuft nicht auf der tatsächlichen Relaunch-Linie

**Risiko:** Gates existieren, schützen aber keine relevanten Pull Requests.

**Mitigation:** CI-Trigger gegen aktuelle Branch-/PR-Wahrheit verifizieren und härten.

## R27-02 — Tests prüfen alte dist-Artefakte

**Risiko:** Grüne Browserläufe sagen nichts über den aktuellen HEAD aus.

**Mitigation:** Isolierte Build-Artefakte + Build-SHA/Path-Evidence.

## R27-03 — Render-Smokes statt Verhaltensnachweis

**Risiko:** Kritische Verträge können brechen, obwohl Komponenten rendern.

**Mitigation:** Behavior Assertions auf Route/State/Network/Persistence.

## R27-04 — Flaky E2E wird mit Retries maskiert

**Risiko:** CI wird scheinbar grün, Regressionen bleiben zufällig.

**Mitigation:** Flake-Policy, deterministische Zustands-Waits, begrenzte Retries.

## R27-05 — Visual Baseline wird blind aktualisiert

**Risiko:** Echte UI-Regressionen werden als neue Wahrheit gespeichert.

**Mitigation:** Baseline-Update-Protokoll + Changelog/Review.

## R27-06 — Consent nur über DOM statt Network getestet

**Risiko:** GTM/GA4 kann trotz grünem Test pre-consent senden.

**Mitigation:** Network-E2E auf reale Provider-Domains/Interception.

## R27-07 — CI erzeugt echte Provider-Side-Effects

**Risiko:** Testleads, Mails oder Analytics verschmutzen Produktion.

**Mitigation:** Testadapter/isolierte Config/DRY_RUN mit expliziter Evidence.

## R27-08 — Route-/SEO-Handspiegel driften

**Risiko:** App, SSR, Sitemap und Search widersprechen sich.

**Mitigation:** Registry-Drift-Guard + HTTP/SEO Integration.

## R27-09 — i18n-Guard prüft nur Teilmenge

**Risiko:** x10-Regressionsfehler bleiben in seltenen Namespaces unentdeckt.

**Mitigation:** Alle launchrelevanten Namespaces maschinell inventarisieren.

## R27-10 — Gate-Status wird zu früh PASS

**Risiko:** AP28-owned Operations-Anteile werden fälschlich als fertig markiert.

**Mitigation:** Owner-bound PARTIAL statt False-ready.

## R27-11 — Shopify-Entscheidung wird durch alte Consumer-Tests zurückgerollt

**Risiko:** Website entwickelt wieder eigenen Checkout/Purchase-Pfad.

**Mitigation:** Canonical Consumer-E2E auf Shopify-Outbound; Legacy Inquiry klar trennen.

## R27-12 — Quality-Dokumente werden parallele Wahrheiten

**Risiko:** QUALITY-GATES/QA-MATRIX/Contracts widersprechen sich.

**Mitigation:** Vorhandene kanonische Dateien konsolidieren und Verweise statt Duplikate nutzen.

# 19. Testdaten- und Fixture-Policy

## 19.1 Erlaubt

- synthetische Personen/Unternehmen
- deterministische E-Mail-Adressen unter klarer Testdomain / nicht zustellbarer Domain
- temporäre SQLite-/Fixture-Datenbanken
- lokale Testadapter
- Fake Clocks
- Fixture Assets ohne Kundendaten
- synthetische GTM-/Analytics-Container-IDs für Network-Tests

## 19.2 Verboten

- echte Leads/Kundendaten
- produktive CRM-Credentials
- produktive Mail-API-Keys
- produktive Analytics-Property mit CI-Traffic
- echte Entitlement-Tokens in Snapshots
- Secrets in Testreportern

## 19.3 Cleanup

Tests müssen:

- eigene IDs besitzen
- isolierte Stores nutzen
- wiederholbar sein
- keinen globalen Zustand zwischen Tests voraussetzen
- nach Möglichkeit automatisch cleanupen

# 20. Visual Regression Policy

Visual Regression dient dem Erkennen unbeabsichtigter Layout-/Design-Änderungen, nicht dem Festschreiben jedes Pixels.

## 20.1 Snapshot-Kandidaten

Bevorzugt:

- Kernseiten
- Design-System-sensitive Patterns
- responsive Breakpoints
- offene Dialog-/Gate-/Menu-Zustände
- lange Locale
- Error/Empty/Success Zustände

## 20.2 Nicht snapshotten

Ohne Stabilisierung ungeeignet:

- Live-Uhrzeit
- dynamische Eventdaten
- externe Widgets
- animierende Zustände mitten in Transition
- zufällige IDs
- personalisierte Provider-Inhalte

## 20.3 Toleranz

Pixel-/Threshold-Werte werden aus realer Rendering-Stabilität abgeleitet. Keine große Toleranz nur um Flakes verschwinden zu lassen.

# 26. False-ready Audit

Closure sucht explizit nach:

- Test existiert, wird aber nie ausgeführt
- CI-Step existiert, triggert nicht auf relevante Branches/PRs
- `continue-on-error` auf Launch-Gate
- globales `test.skip`/`fixme` auf kritischem Pfad
- überhöhte Retries
- feste Sleeps statt Zustands-Waits
- Visual Baseline blind aktualisiert
- Snapshot Threshold übermäßig gelockert
- axe nur auf leere/statische Seite
- 404-Test prüft Text statt Status
- Redirect-Test akzeptiert beliebigen `<400`
- Sitemap-Test prüft nur XML-Existenz
- hreflang-Ziele nicht erreichbar
- i18n-Guard prüft nur Home
- Consent-Test prüft nur dataLayer statt Network
- Pre-consent Event später replayed
- Conversion vor Persistenz
- CRM-Test ruft echten Provider
- Consumer-Test behauptet Kauf statt Shopify-Outbound/Inquiry
- Lead-Magnet-Test verwendet öffentliche Fixture-URL
- Security-/Performance-Gates dokumentiert, aber nicht CI-reachable
- alte `dist`-Artefakte statt aktuellem Build
- Testdaten mit PII/Secrets
- Gate 12 vor AP28 vollständig PASS behauptet, obwohl Backup/Rollback noch owner-bound ist

False-ready Findings > 0 verhindern AP27-CLOSURE PASS, sofern sie AP27-owned und launchkritisch sind.
