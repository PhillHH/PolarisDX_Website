# 0. Zweck und Rolle von AP10

AP10 ist der zentrale Routing-/HTTP-Konsolidierungspunkt des Relaunchs.

Vor AP10 existiert Routing-Wahrheit historisch an mehreren Stellen parallel:

- `src/App.tsx` — tatsächlich deklarierte App-Routes,
- `server.ts` — `SITEMAP_ROUTES`, `EXTRA_KNOWN_PATHS`, `KNOWN_PATHS`, `isKnownPath`, Redirects und HTTP-Status,
- `src/hooks/useSearch.ts` — Search-Ziele,
- AP09 SEO/Sitemap-Route-Source — Canonical-/hreflang-/Sitemap-Ziele,
- dazu einzelne Navigation-/Footer-/Prerender-/Test-Spiegel.

Diese Handpflege ist ein strukturelles Risiko:

> Eine Route kann im Browser rendern und trotzdem serverseitig `404` liefern, wenn sie nicht in der Known-Path-Logik gespiegelt wurde.

AP10 beseitigt genau dieses Risiko.

Der zentrale Qualitätsgrundsatz lautet:

> **Eine öffentliche Route, ihre HTTP-Semantik, ihre Redirect-Regeln und alle technischen Konsumenten müssen aus einer konsistenten Routing-Wahrheit ableitbar sein.**

AP10 besitzt vier Aufgabenfelder:

1. echte permanente Redirects für bereits bekannte Migrationspfade,
2. eine vollständige aktuelle Redirect Map für den bereits bekannten Bestand,
3. eine zentrale Route Registry / Known-Path-Wahrheit,
4. eine automatisierte 200/301/404-Regression über die zehn Projektsprachen.

AP10 ist außerdem die technische Vorbedingung für die anschließende breite Seitenphase AP11–AP21.

Nach PT10.3 soll eine neue Route nicht mehr manuell an vier bis fünf Stellen synchronisiert werden müssen.

# 6. AP10 Routing Contract

## 6.1 Locale Prefix Contract

Öffentliche Seiten verwenden ein Locale-Präfix.

Unpräfixierte bekannte Seitenroute:

→ `301` auf dieselbe logische Seite unter `/de/...`.

Querystring muss erhalten bleiben, soweit technisch relevant.

URL-Fragmente (`#...`) werden bei echten HTTP-Requests nicht an den Server übertragen und können daher serverseitig nicht migriert werden.

Clientseitige Altanker werden nur dort bewahrt, wo sie real im Client bekannt sind.

## 6.2 Redirect Status Contract

Permanente Migrationsregeln:

`301`.

Nicht:

- 200 + clientseitiges `<Navigate>`,
- 302 ohne Grund,
- Meta Refresh,
- JS-only Redirect als primärer Migrationsmechanismus.

## 6.3 Redirect-Hop Contract

Bekannte Migrationsquelle soll im Regelfall in genau einem Hop das kanonische Ziel erreichen.

Ziel:

`redirect hops = 1`

Ausnahmen nur mit dokumentiertem Grund.

Loops = 0.

## 6.4 Canonical Target Contract

Redirect-Ziel muss:

- real existieren,
- 200 liefern,
- kanonische Route sein,
- richtige Locale besitzen,
- nicht erneut redirecten,
- nicht noindex sein, sofern öffentliche indexierbare Migration.

## 6.5 Dynamic Route Contract

Dynamische Routes dürfen nicht nur aufgrund eines generischen Patterns als bekannt gelten.

Beispiele:

`/diagnostics/:slug`

ist nur real, wenn `:slug` in der aktuellen Service-Datenquelle existiert.

`/articles/:slug`

ist nur real, wenn veröffentlichter Article Slug existiert.

`/epigenetics/musterbefund/:slug`

ist nur real, wenn Befund-Slug existiert.

Unbekannter dynamischer Slug:

`404`.

## 6.6 404 Contract

Unbekannte öffentliche Route:

- HTTP `404`,
- NotFound UI,
- `noindex, follow`,
- kein Canonical,
- kein hreflang,
- keine Sitemap-Mitgliedschaft.

Keine Soft-404.

## 6.7 Route Registry Contract

Die zentrale Route Registry muss mindestens ausdrücken können:

- route id,
- path / path pattern,
- route kind,
- component/logical owner,
- locale behavior,
- indexability,
- sitemap eligibility,
- search eligibility,
- dynamic source, falls vorhanden,
- known-path behavior,
- redirect-source/target relationships,
- ggf. SEO-/navigation metadata only where technically appropriate.

Sie soll Daten liefern,
nicht React-/SEO-/Search-Verhalten untrennbar vermischen.

## 6.8 Registry Consumer Contract

Mindestens folgende technische Konsumenten müssen nach PT10.3 dieselbe Route-Wahrheit konsumieren:

1. App Routes,
2. serverseitige Known Paths,
3. Sitemap Route Source,
4. Search Route Targets / Route Eligibility,
5. Redirect Validation / Targets,
6. SEOHead Route Awareness,
7. Route-/HTTP-Tests.

## 6.9 No Fifth Mirror

Nach PT10.3 darf kein neuer manueller fünfter Route-Katalog entstehen.

Veraltete Spiegel müssen:

- entfernt,
- generiert,
- registry-adaptiert,
- oder klar Legacy/Non-authoritative

sein.

## 6.10 Route Addition Rule

Nach PT10.3 soll eine neue Route über einen klaren Registry-Workflow ergänzt werden.

Dabei müssen relevante Ableitungen automatisch oder guard-gesichert aktualisiert werden.

Eine neue Route darf nicht mehr unbemerkt:

- im Browser 200 rendern,
- serverseitig 404 liefern,
- in Search fehlen,
- in Sitemap fehlen,
- falsche SEO-Metadaten erhalten.

- ggf. Redirect-Zielbeziehung.

## 9.3 App Routes

App Routing muss die Registry nutzen oder aus ihr deterministisch ableitbar sein.

Keine zweite manuelle Liste daneben erhalten,
wenn technisch vermeidbar.

React lazy imports können getrennt bleiben,
wenn das die Registry sauberer hält.

Ziel ist gemeinsame Route-Metadaten-Wahrheit,
nicht zwangsläufig eine einzige Datei mit sämtlicher UI-Logik.

## 9.4 Known Paths

Serverseitige Known-Path-Logik aus Registry ableiten.

Keine getrennte manuelle:

`EXTRA_KNOWN_PATHS`

oder gleichwertige Liste,
sofern sie dieselbe Route-Wahrheit dupliziert.

Dynamische Slugs gegen reale Datenquelle validieren.

## 9.5 Sitemap

AP09 Sitemap Route Source auf Registry umstellen.

Dabei AP09-Invarianten erhalten:

- x10,
- indexable only,
- canonical only,
- honest lastmod,
- keine 404,
- keine Redirect Sources.

## 9.6 Search

AP07 Search Route-Ziele / Eligibility aus Registry speisen,
wo technisch sinnvoll.

Nicht Search UI neu bauen.

Search Content/Metadata kann weiterhin eigene Datenquelle besitzen.

Aber Route-Pfad/Existenz darf nicht manuell abweichen.

## 9.7 Redirects

Redirect Targets gegen Registry validieren.

Redirect Source muss bewusst als Legacy/Redirect klassifiziert sein.

Kein Redirect auf unbekanntes Registry-Ziel.

## 9.8 SEOHead

AP09 SEOHead Route Awareness auf Registry umstellen,
wo technisch erforderlich.

Nicht SEOHead neu designen.

Canonical/hreflang-Eligibility muss mit Registry-Indexability konsistent sein.

## 9.9 Tests aus derselben Wahrheit

Route-/HTTP-Testmatrix muss aus Registry generierbar sein.

Keine separate manuelle Testliste,
die wieder driften kann.

Mindestens:

- statische 200-Routen,
- dynamische gültige Slugs,
- Sitemap-eligible Routes,
- Search-eligible Routes,
- Redirect Sources,
- noindex/non-public classifications.

## 9.10 Guard G1 — Route Registry Parity

Erstelle oder erweitere genau einen kanonischen Guard G1.

Er prüft mindestens:

1. App Route ↔ Registry,
2. Registry ↔ Known Path,
3. Registry ↔ Sitemap,
4. Registry ↔ Search,
5. Registry ↔ SEO Route Awareness,
6. Redirect Target Exists,
7. dynamische Datenquellen valide,
8. keine duplicate Route IDs,
9. keine duplicate canonical paths,
10. keine veralteten Handspiegel.

## 9.11 G1 Hard Failure

Non-Zero bei:

- App Route ohne Registry-Eintrag,
- Registry Public Route ohne App Route,
- Known Path Drift,
- Sitemap Drift,
- Search Target ohne Route,
- Redirect Target unbekannt,
- duplicate route id/path.

## 9.12 CI

G1 muss in der aktuellen Relaunch-CI laufen.

Keine AP27-Gesamtplattform vorziehen.

## 9.13 Veraltete Prerender-Liste

`scripts/prerender.mjs` darf nach PT10.3 nicht als glaubwürdige konkurrierende Route-SSOT verbleiben.

Wenn aktiv:

Registry-getrieben machen.

Wenn Legacy:

klar deaktiviert/non-authoritative dokumentieren.

## 9.14 Header/Footer

Header/Footer müssen nicht vollständig aus Registry generiert werden.

Navigation ist eine kuratierte IA,
nicht identisch mit Route Registry.

Aber:

alle nav/footer Targets müssen registry-valid sein.

G1 oder ergänzender Validator darf das prüfen.

404.

# 12. Risikoregister

## R10-01 — Browser route works, server says 404

**Risiko:** App- und Known-Path-Drift.  
**Mitigation:** zentrale Registry + G1.

## R10-02 — Client-only redirect returns 200

**Risiko:** Rankings/HTTP-Semantik falsch.  
**Mitigation:** PT10.1 echte 301 + G9.

## R10-03 — Redirect loop

**Risiko:** Nutzer/Bots hängen in Schleife.  
**Mitigation:** Redirect-Graph-/Matrix-Test.

## R10-04 — Redirect chain

**Risiko:** unnötige Hops / Crawl-/Performance-Verlust.  
**Mitigation:** Direktziel in Redirect Map.

## R10-05 — Dynamic wildcard accepts fake slug

**Risiko:** Soft-404/false-known path.  
**Mitigation:** echte Datenquelle statt Pattern-only.

## R10-06 — Registry becomes monolith

**Risiko:** technische Superdatei mit UI-/SEO-Logik.  
**Mitigation:** Metadaten-/Adaptergrenzen.

## R10-07 — Navigation mistaken for Registry

**Risiko:** kuratierte IA wird automatisch aus allen Routes generiert.  
**Mitigation:** Navigation bleibt eigener kuratierter Consumer.

## R10-08 — AP09 regression

**Risiko:** Sitemap/Canonical/hreflang brechen bei Registry-Umschaltung.  
**Mitigation:** PT10.3/4 SEO-/Sitemap-Regressionssuite.

## R10-09 — AP07 Search regression

**Risiko:** Search verliert Content-/Metadata bei Registry-Umschaltung.  
**Mitigation:** nur Route Eligibility/Existence zentralisieren, Search Content Contract erhalten.

## R10-10 — Legacy catalogue remains authoritative-looking

**Risiko:** `prerender.mjs` oder alte Listen driften weiter.  
**Mitigation:** registry-driven oder klar Legacy/non-authoritative.

## R10-11 — AP29 pulled forward

**Risiko:** AP10 versucht unbekannte externe Alt-URLs zu raten.  
**Mitigation:** nur aktuell bekannte Map; externe Discovery → AP29.

## R10-12 — False 404 test

**Risiko:** Test prüft nur sichtbaren Text statt HTTP Status.  
**Mitigation:** echte `response.status()` Assertions + G2.
