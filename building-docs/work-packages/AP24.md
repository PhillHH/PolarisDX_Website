# 0. Zweck und Rolle von AP24

AP24 ist das systemweite Accessibility-Härtungspaket des Website-Relaunches.

Es baut auf den bereits bestehenden seiten-/journey-spezifischen Accessibility-Checks aus früheren APs auf und führt diese zu einem konsistenten systemweiten Qualitätsvertrag zusammen.

Historisch war Accessibility im Repository nur **minimal** abgesichert:

- `eslint-plugin-jsx-a11y` war vorhanden,
- einzelne jsx-a11y-Befunde waren offen,
- es gab keinen belastbaren siteweiten axe-Lauf,
- keine reproduzierbare dynamische Zustandsmatrix,
- keine vollständige manuelle Screenreader-Checkliste.

AP24 schließt diese Lücke.

Wichtig:

**AP24 setzt WCAG 2.2 AA als Qualitätsziel.**

AP24 behauptet keine formale Zertifizierung, keine externe Konformitätsprüfung und keine rechtliche Garantie.

# 8. Semantik Contract

Native Semantik zuerst.

Bevorzugt:

- `<header>`
- `<nav>`
- `<main>`
- `<footer>`
- `<section>` mit sinnvoller Überschrift
- `<button>`
- `<a>`
- `<form>`
- `<label>`
- `<fieldset>/<legend>`
- `<table>/<th>`

ARIA:
nur ergänzend.

Nicht:
native Semantik mit widersprüchlichen Rollen überschreiben.

---

# 9. Landmark Contract

Jede Seite:

- genau ein sinnvoller Main
- Navigation eindeutig
- Footer korrekt
- Search als Search-Landmark nur, wenn sinnvoll
- keine redundanten Rollen wie `role="navigation"` auf nativer `<nav>` ohne Grund

Mehrere Navigationsbereiche:
accessible label.

---

# 10. Heading Contract

Headings spiegeln die Dokumentstruktur.

Regeln:

- H1 seitenbezogen
- Folgeebenen logisch
- keine Nutzung als reines Styling-Primitive
- keine versteckten leeren Headings
- keine unnötige Heading-Duplizierung durch Desktop/Mobile

Komponenten dürfen keine starre Heading-Stufe erzwingen, wenn Parent-Kontext variabel ist.

---

# 11. Listen / Tabellen

Listen:
native `<ul>/<ol>`.

Tabellen:
nur für tabellarische Daten.

Bei Tabellen:

- Headerzellen
- Scope/Associations soweit nötig
- Caption oder nachvollziehbarer Kontext
- responsive Darstellung ohne Bedeutungsverlust

Layout:
keine Tabellen.

---

# 12. Buttons vs Links

Button:
führt eine Aktion aus.

Link:
navigiert.

Nicht:

- `<div onClick>`
- `<span onClick>`
- `href="#"` als pseudo button
- Link mit Button-Role ohne echten Bedarf

Disabled:
semantisch korrekt und nachvollziehbar.

---

# 13. Form Labels

Jedes Control:

- sichtbares Label oder bewusstes zugängliches Name-Konzept
- programmatische Verbindung
- Required State nicht nur visuell
- Placeholder nicht als alleiniger Labelersatz

Gruppen:
`fieldset/legend` oder gleichwertig.

---

# 14. Fehlersemantik

Fehler:

- verständlicher Text
- field-specific, wo möglich
- programmatic relation
- `aria-invalid`/description nur sinnvoll eingesetzt
- Summary, wenn Formulargröße dies rechtfertigt

Nach Submit:
Fokusstrategie bewusst.

---

# 15. Statusmeldungen

Asynchron:

- Loading
- Saving
- Success
- Retry
- Error
- Search result update
- Form validation summary

müssen für Assistive Technology wahrnehmbar sein.

Nicht jede kleine visuelle Änderung braucht Live Region.

Live Regions:
sparsam, state-truthful.

---

# 16. Tastatur Contract

Alle Interaktionen:

- Tab
- Shift+Tab
- Enter
- Space
- Escape, wo Pattern dies verlangt
- Arrow Keys, wenn ARIA Pattern/Widget dies verlangt

Keine Funktion:
nur hover/mouse.

---

# 17. Header / Mega-Menü

Keyboard:

- Trigger fokussierbar
- Enter/Space öffnet
- Escape schließt
- Fokus bleibt logisch
- Tab kann sinnvoll durch Inhalte gehen
- kein Fokusverlust bei Close
- `aria-expanded`
- `aria-controls` nur wenn real
- mobile/desktop duplicated DOM darf keine doppelten Tab Stops erzeugen

---

# 18. Mobile Menü

Muss:

- trigger accessible name
- expanded state
- keyboard order
- focus handling
- close behavior
- background interaction passend zum Modalitätsmodell

Wenn modal:
Trap korrekt.

Wenn nicht modal:
kein unnötiger Trap.

---

# 19. Search

Search Input:

- accessible label
- submit/clear controls
- result count/status
- keyboard navigation durch Vorschläge, falls Suggestions
- Escape semantics
- focus return/retention
- no hidden duplicate focusable results

# 21. Modals / Drawers

Echte Modal Dialogs:

- `role="dialog"` / native dialog-equivalent
- accessible name
- modal semantics
- initial focus
- focus containment
- Escape
- close button
- focus return

Drawers:
Modalität bewusst entscheiden.

Kein Focus Trap nur weil UI seitlich einfliegt.

# 22. ChapterNav / On-page Navigation

- Links oder Buttons semantisch korrekt
- keyboard
- active state nicht nur Farbe
- Hash Navigation
- Scroll Offset
- Fokusverhalten
- reduced motion

---

# 23. Slider / Carousel

Wenn interaktiv:

- Controls accessible names
- keyboard
- current/total context
- no autoplay ohne Kontrolle
- pause where required
- reduced motion

Wenn nur dekorativ:
keine unnötigen interaktiven Rollen.

---

# 24. Visible Focus

Fokusindikator:

- klar sichtbar
- nicht durch `outline: none` entfernt
- nicht abgeschnitten
- auf hell/dunkel ausreichend kontrastreich
- konsistent mit Designsystem

Prefer:
tokenisierte Focus Ring Styles.

---

# 25. Focus Trap

Nur bei:

echtem modalem Zustand.

Nicht bei:

- normaler Navigation
- Inline Search
- nichtmodalem Drawer
- Accordions

Nested Modals:
vermeiden; wenn real, eindeutig testen.

---

# 26. Focus Return

Close/Submit/Cancel:

Fokus zum auslösenden Element zurück,
wenn dieses noch existiert.

Falls nicht:
sinnvoller logischer Fokuspunkt.

---

# 27. Skip Link

- erstes/nahe erstes focusable Element
- sichtbar bei Fokus
- Ziel = Main
- Main ggf. programmatisch fokussierbar
- funktioniert bei SSR/Hydration
- nicht durch fixed header verdeckt

---

# 28. Route Change Focus

SPA Navigation ist Accessibility-relevant.

AP24 muss entscheiden und dokumentieren:

- Fokus auf Main/H1?
- Fokus unverändert?
- Announcement?

Entscheidung:
durch reale UX-/Screenreader-Tests.

Kein blindes globales `focus()` ohne Evidence.

---

# 29. Hash Focus / Scroll

Hash/Chapter Link:

- scrollt korrekt
- fixed-header Offset
- reduced motion
- Ziel semantisch sinnvoll
- Fokus nur setzen, wenn Keyboard-/AT-Navigation dadurch verbessert wird

# 30. Contrast Contract

WCAG AA Zielwerte werden anhand tatsächlicher Textgröße/Komponente geprüft.

Prüfen:

- Body text
- muted text
- links
- buttons
- inputs
- placeholders, soweit relevant
- focus rings
- icons
- status text
- dark brand surfaces
- disabled states soweit bedeutungstragend

---

# 31. Brand Surfaces

Besonders:

- dunkle Markenflächen
- Green/Forest Surfaces
- Accent Tints
- Badges
- Cards
- Hero Overlays

Token-first Fix.

Keine page-spezifischen zufälligen Farbwerte, wenn Designsystem korrigiert werden kann.

---

# 32. Befund-/Statusfarben

Kein:

- Grün = gut ohne Text/Icon
- Rot = schlecht ohne Text/Icon
- nur farbiger Ring/Chart-Segment ohne Label

Zusätzliche Semantik:

- Text
- Icon
- Pattern
- Label
- Table
- legend

---

# 33. Charts

Chart:

- Titel
- Beschreibung/Context
- Text-/Tabellenalternative für wesentliche Werte/Trends
- Farben mit ausreichender Unterscheidbarkeit
- Information nicht nur über Farbe
- Tooltip-only Content darf nicht die einzige Quelle sein

---

# 34. Alt Text

Informativ:

beschreibt relevante Funktion/Information im Kontext.

Nicht:

- Datei-/Assetname
- keyword stuffing
- „Bild von“ automatisch
- redundanter sichtbarer Text

Dekorativ:

`alt=""`
oder korrekt aus Accessibility Tree entfernen.

---

# 35. Icons

Icon-only Button:

accessible name.

Dekoratives Icon innerhalb gelabeltem Button:
`aria-hidden`/equivalent.

Nicht doppelt:
Icon label + Text label + redundant role.

---

- große Entrance Animations reduzieren/deaktivieren
- Smooth Scroll reduzieren
- Parallax vermeiden
- Carousel Autoplay stoppen/reduzieren
- funktionale Progress-/State-Anzeige erhalten

# 43. AP24 Invarianten

## A11Y-01 — Predecessor Integrity

AP23 muss COMPLETE / AP23-CLOSURE PASS sein, bevor AP24 produktiv startet.

## A11Y-02 — Target Standard

WCAG 2.2 AA ist das verbindliche Qualitätsziel für die öffentliche Website; AP24 behauptet keine Zertifizierung.

## A11Y-03 — One Main Landmark

Jede öffentliche Seite besitzt genau einen sinnvollen `<main>`-Landmark.

## A11Y-04 — Landmark Semantics

Header, Navigation, Main, Footer, Search und ergänzende Regionen verwenden semantisch korrekte Landmarks ohne redundante Rollen.

## A11Y-05 — Heading Hierarchy

Heading-Hierarchien sind logisch, seitenbezogen und frei von künstlichen Sprüngen, soweit Inhalt/Komponenten dies erlauben.

## A11Y-06 — Lists and Tables

Listen und Tabellen verwenden native semantische Strukturen; Tabellen haben nachvollziehbare Header-/Caption-Semantik, soweit eingesetzt.

## A11Y-07 — Buttons vs Links

Aktionen sind Buttons; Navigation ist Link; keine semantischen Click-Divs als primäre Interaktion.

## A11Y-08 — Form Labels

Jedes relevante Form Control besitzt programmatisch verknüpftes Label/Accessible Name.

## A11Y-09 — Form Errors

Validierungsfehler sind programmatisch mit Feldern verbunden und werden verständlich beschrieben.

## A11Y-10 — Status Announcements

Asynchrone Lade-, Erfolgs-, Fehler- und Statusmeldungen sind für Assistive Technology sinnvoll angekündigt.

## A11Y-11 — Keyboard Complete

Alle Kernpfade sind vollständig per Tastatur nutzbar.

## A11Y-12 — No Keyboard Trap

Es existiert kein unbeabsichtigter Keyboard Trap.

## A11Y-13 — Header Navigation

Header-/Mega-Menü ist keyboard-operable, verständlich fokussierbar und schließbar.

## A11Y-14 — Mobile Navigation

Mobile Navigation ist keyboard-/screenreader-kompatibel und besitzt korrekte expanded/state-Semantik.

## A11Y-15 — Search Keyboard

Suche inklusive Vorschlägen/Ergebnissen ist per Tastatur bedienbar und besitzt klare Fokus-/Statussemantik.

## A11Y-16 — Consent Keyboard

Cookie-/Consent-UI bleibt vollständig keyboard-/focus-safe.

## A11Y-17 — Modal and Drawer Keyboard

Modals/Drawers besitzen korrekte Dialogsemantik, Fokusführung, Escape-Verhalten und Focus Return.

## A11Y-18 — ChapterNav Keyboard

ChapterNav/On-page Navigation ist per Tastatur bedienbar und unterstützt nachvollziehbare Hash-/Section-Navigation.

## A11Y-19 — Slider Keyboard

Slider/Carousels sind entweder vollständig keyboard-bedienbar oder werden auf eine zugängliche nicht-interaktive Alternative reduziert.

## A11Y-20 — Visible Focus

Alle interaktiven Elemente besitzen einen sichtbaren Fokusindikator mit ausreichendem Kontrast.

## A11Y-21 — Focus Trap Correctness

Focus Trap wird nur in echten modal blockierenden Kontexten verwendet und nie in normalen Seiten-/Drawer-Situationen, wo er Navigation einschränkt.

## A11Y-22 — Focus Return

Nach Schließen von Modal/Menu/Drawer kehrt Fokus nachvollziehbar zum auslösenden Element oder sinnvollen Ersatz zurück.

## A11Y-23 — Skip Link

Ein sichtbarer-on-focus Skip Link führt zuverlässig zum Main Content.

## A11Y-24 — Route Change Focus

SPA-/SSR Route Changes besitzen eine bewusste, testbare Fokusstrategie ohne überraschenden Fokusverlust.

## A11Y-25 — Hash Focus and Scroll

Hash-/Chapter-Navigation scrollt zum Ziel und setzt Fokus nur dort, wo dies für Tastatur/Screenreader sinnvoll und konsistent ist.

## A11Y-26 — Text Contrast

Normaler und großer Text erfüllt WCAG-AA-Kontrastanforderungen.

## A11Y-27 — Interactive Contrast

Buttons, Links, Inputs und sichtbare Zustände erfüllen relevante Kontrastanforderungen.

## A11Y-28 — Non-text Contrast

Icons, Input-Borders, Fokusindikatoren, Charts und andere bedeutungstragende UI-Grafiken erfüllen Non-text-Contrast, soweit WCAG verlangt.

## A11Y-29 — Brand Surface Contrast

Text-/Akzentkombinationen auf dunkleren Markenflächen im Light Theme sind kontrastgeprüft.

## A11Y-30 — Result and Chart Colors

Befund-/Status-/Chart-Farben transportieren Information nie ausschließlich über Farbe.

## A11Y-31 — Alt Text

Informative Bilder besitzen kontextgerechte Alt-Texte.

## A11Y-32 — Decorative Images

Dekorative Bilder/Icons sind für Assistive Technology korrekt ausgeblendet oder leer alt-markiert.

## A11Y-33 — Chart Alternatives

Charts/Datavisualisierungen besitzen eine textliche oder tabellarische Alternative für die wesentliche Information.

## A11Y-34 — Reduced Motion

`prefers-reduced-motion` wird für nicht notwendige Animationen/Transitions respektiert.

## A11Y-35 — No Motion Dependency

Keine wesentliche Information oder Bedienung hängt von Animation/Motion ab.

## A11Y-36 — Automated Axe Gate

axe/Playwright läuft gegen definierte Kernseiten/-zustände; serious/critical Findings = 0.

## A11Y-37 — jsx-a11y Gate

`eslint-plugin-jsx-a11y` bleibt aktiv; neue relevante Accessibility-Lintfehler = 0 und bekannte AP24-owned Findings werden geschlossen.

## A11Y-38 — Manual Screenreader Checklist

Eine reproduzierbare manuelle Screenreader-Checkliste deckt Kernpfade und zentrale Komponenten ab.

## A11Y-39 — Representative State Coverage

Automatisierte A11y-Checks decken nicht nur statische Seiten, sondern auch Menüs, Modals, Formfehler, Consent, Search und relevante dynamische Zustände ab.

## A11Y-40 — Closure Boundary

AP25 bleibt NOT STARTED bis AP24-CLOSURE PASS; AP25 besitzt Performance, nicht Accessibility-Fixes außer konkrete Perf/A11y-Interaktion.

# 44. Risikoregister

## R24-01 — Axe wird nur auf statischen Seiten ausgeführt und verpasst echte Interaktionsprobleme

**Risiko:** Axe wird nur auf statischen Seiten ausgeführt und verpasst echte Interaktionsprobleme.

**Mitigation:** Stateful Playwright-Axe-Matrix für Menüs, Search, Consent, Modals, Formfehler und dynamische Zustände.

## R24-02 — Native Semantik wird durch ARIA überschrieben

**Risiko:** Native Semantik wird durch ARIA überschrieben.

**Mitigation:** native-first Regel; ARIA nur dort, wo native Elemente nicht ausreichen; redundant/konfliktäre Rollen vermeiden.

## R24-03 — Focus Trap blockiert Nutzer in nicht-modalem Drawer oder Menü

**Risiko:** Focus Trap blockiert Nutzer in nicht-modalem Drawer oder Menü.

**Mitigation:** Trap nur für echte modale Kontexte; Regressionstest für Escape/Tab/Shift+Tab.

## R24-04 — Kontrastfixes beschädigen Designsystem inkonsistent

**Risiko:** Kontrastfixes beschädigen Designsystem inkonsistent.

**Mitigation:** Token-first Korrekturen; lokale Ausnahmen nur dokumentiert; Visual Regression Handoff an AP27.

## R24-05 — Dunkle Markenflächen bestehen visuell, aber Text/Icons fallen unter AA

**Risiko:** Dunkle Markenflächen bestehen visuell, aber Text/Icons fallen unter AA.

**Mitigation:** dedizierte Brand-Surface-Contrast-Matrix inklusive Hover/Focus/Disabled States.

## R24-06 — Befund-/Chartfarben sind nur farbcodiert

**Risiko:** Befund-/Chartfarben sind nur farbcodiert.

**Mitigation:** zusätzliche Labels, Pattern, Text, Icons oder Tabellenalternative.

## R24-07 — Alt-Texte werden generisch oder keyword-stuffed

**Risiko:** Alt-Texte werden generisch oder keyword-stuffed.

**Mitigation:** kontextbezogene Alt-Text-Regeln; dekorative Medien leer; keine SEO-Phrasen als Accessibility-Text.

## R24-08 — Route Change Fokus wird aggressiv auf H1 gesetzt und stört Maus-/Screenreader-Nutzer

**Risiko:** Route Change Fokus wird aggressiv auf H1 gesetzt und stört Maus-/Screenreader-Nutzer.

**Mitigation:** Fokusstrategie empirisch testen; nur kontrolliert und nachvollziehbar einsetzen.

## R24-09 — Reduced Motion deaktiviert funktionale Zustandswechsel oder versteckt Content

**Risiko:** Reduced Motion deaktiviert funktionale Zustandswechsel oder versteckt Content.

**Mitigation:** nur nicht essentielle Motion reduzieren; Inhalt und State Transition bleiben sichtbar.

## R24-10 — Automatisierte Tests erzeugen trügerischen PASS trotz Screenreader-Problemen

**Risiko:** Automatisierte Tests erzeugen trügerischen PASS trotz Screenreader-Problemen.

**Mitigation:** manuelle Screenreader-Checkliste als eigener Closure-Gate; keine WCAG-Zertifizierung behaupten.

## R24-11 — Fixes ziehen AP25-Performance-Optimierung oder AP27-Quality-Plattform vor

**Risiko:** Fixes ziehen AP25-Performance-Optimierung oder AP27-Quality-Plattform vor.

**Mitigation:** AP24 nur accessibility-owned Änderungen; Performance-/Visual-Regression-Handoffs dokumentieren.

## R24-12 — Neue/alte Komponenten haben unterschiedliche A11y-Muster

**Risiko:** Neue/alte Komponenten haben unterschiedliche A11y-Muster.

**Mitigation:** gemeinsame Komponenten und Accessibility-Primitives bevorzugen; kein page-spezifischer Sondercode ohne Notwendigkeit.
