# 0. Zweck und Rolle von AP05

AP05 konsolidiert die bestehende **Sales-Machine-Art-Direction** als verbindliches, reproduzierbares UI-System im **Light Theme**.

AP05 erfindet kein neues Design. Es macht das vorhandene Zielbild technisch eindeutig und wiederverwendbar.

Die zentralen Ziele sind:

1. Sales-Machine-Farben, Tokens und Light Theme als einzige Relaunch-Basis festschreiben.
2. Typografie vollständig und ohne externe Font-CDN-Abhängigkeit standardisieren.
3. Core UI-Komponenten für spätere Seiten-APs konsolidieren.
4. wiederkehrende Sales-Machine-Layoutmuster katalogisieren und vereinheitlichen.
5. Motion, Reduced Motion, Visual Regression und Error-State-Patterns technisch absichern.

Der zentrale Grundsatz lautet:

> AP05 konsolidiert die bestehende Sales-Machine-Art-Direction. `redesign/preview` darf ausschließlich art-direction-neutrale QA-, Test- und System-Patterns liefern, niemals eine alternative visuelle Richtung.

# 3. Verbindliche Designentscheidungen

## 3.1 Sales-Machine ist die Art Direction

Verbindlich:

- Sales-Machine aus `feat/home-leadmagnet` ist die visuelle Basis.
- bestehende Relaunch-Linie übernimmt diese Richtung.
- AP05 darf sie konsolidieren, nicht ersetzen.

## 3.2 Light Theme ist der einzige Relaunch-Default

Verbindlich:

- Light Theme.
- keine Dark-Theme-Alternative.
- kein Theme-Switcher.
- keine parallele Dark-Token-Palette.
- keine Dark-Screens als zweite Produktoberfläche.

Dunkle Flächen innerhalb eines Light Themes sind zulässig, z. B. Navy CTA/Footer/Hero-Kontrastflächen. Das ist **kein Dark Theme**.

## 3.3 `redesign/preview` nur für neutrale Patterns

Zulässig aus `redesign/preview`:

- Testaufbau;
- Visual-Regression-Patterns;
- Error Boundary Pattern;
- Komponenten-Testmuster;
- technische Accessibility-/Interaction-Patterns;
- neutrale State-/Dialog-Patterns.

Nicht zulässig:

- alternative Farben;
- Archon-Art-Direction;
- alternative Typografie;
- alternative Branding-Sprache;
- alternative Radius-/Shadow-/Hero-Sprache, wenn diese Sales-Machine widerspricht.

## 3.4 Bekannte aktuelle Design-Baseline

Aktuell dokumentierte Design-Signale, vor Nutzung im Repository neu verifizieren:

### Marke

- `brand.navy` / `brand.deep` / `heading`: `#083358`
- `brand.navy-hover` / `brand.navy-mid`: `#0a3f63`
- `brand.blue` / `brand.primary` / `accentBlue`: `#0d527f`
- `brand.blue-bright` / `brand.secondary`: `#2f6fa0`

### Akzent

- `accent.DEFAULT`: `#0d9488`
- `accent.strong`: `#0f766e`
- `accent.line`: `#14b8a6`
- `accent.soft`: `#f0fdfa`
- `accent.border`: `#99f6e4`
- `accent.on-dark`: `#2dd4bf`

### Semantik

- `success` bewusst getrennt von Akzent
- Befundfarben `red / amber / green` als eigene semantische Familie

### Neutralfarben

Bekannt:

- `ui.border`
- `ui.border-hover`
- `ui.text-muted`
- `ui.field`

### Typografie

Bekannte Pipeline:

`Inter Variable → Inter → Inter Fallback → system-ui → sans-serif`

### bekannte Skalen

# 6. PT05.1 — Visuelle Baseline und Tokens

## 6.1 Ziel

Die Sales-Machine-Farb-/Tokenbasis so konsolidieren, dass spätere Seiten keine freien Hexwerte, konkurrierenden Tokenfamilien oder alternative Art Direction einführen können.

## 6.2 Aufgaben

### ST05.1.1 — Tokeninventar

Aktuellen Repository-State prüfen:

- Tailwind Colors;
- CSS Custom Properties;
- Raw Hex;
- arbitrary color classes;
- Legacy aliases;
- Section-level color constants;
- SVG fill/stroke values;
- semantic colors.

Klassifizieren:

- canonical;
- semantic;
- legacy alias;
- duplicate;
- deprecated;
- forbidden raw value.

### ST05.1.2 — Sales-Machine-Tokens als Basis

Verbindlich:

- bestehende Sales-Machine-Farbwelt erhalten;
- Navy/Blue/Teal-System konsolidieren;
- keine Archon-/Dark-Palette übernehmen;
- keine zweite Brand-Farbwelt.

### ST05.1.3 — Light Theme festschreiben

Technisch sicherstellen:

- Light ist Default und einziges Relaunch-Theme;
- keine `dark:`-basierte alternative Produktoberfläche;
- keine Theme-Switcher-Abhängigkeit;
- keine parallelen Dark Tokens.

Dunkle Komponentenflächen sind als normale Light-Theme-Komponenten zulässig.

### ST05.1.4 — Legacy-Aliase klassifizieren

Bekannte Aliase wie:

- `brand.primary`
- `brand.deep`
- `brand.secondary`
- ggf. `accentBlue`
- Legacy Gray Tokens

prüfen.

Entscheiden:

- Alias beibehalten als Übergang;
- Call-Sites konsolidieren;
- deprecaten.

Keine großflächige unnötige Migration nur für Namensästhetik.

### ST05.1.5 — Befund-/Statusfarben Kontrast

Prüfen:

- Befund Red/Amber/Green;
- success/warning/error;
- Text auf Soft-Flächen;
- Icons/Charts;
- Beschriftungen.

Bedeutung darf nicht ausschließlich über Farbe vermittelt werden.

AP24 bleibt umfassender A11y-Owner; AP05 muss aber offensichtliche Token-Kontrastprobleme nicht konservieren.

### ST05.1.6 — Neutralfarben WCAG

Prüfen insbesondere:

- `ui.field`
- border states
- muted text
- placeholder
- disabled
- focus rings
- interactive boundaries

Interaktive Grenzen mindestens ausreichend kontrastfähig.

### ST05.1.7 — Spacing / Radius / Shadow

Konsolidieren:

- spacing rhythm;
- card spacing;
- section spacing;
- radius scales;
- `rounded-section`;
- card shadow;
- overlay/dialog shadow;
- glass/glow nur wenn Sales-Machine-konform.

Keine neue Designrichtung.

### ST05.1.8 — Motion Tokens

Definieren/konsolidieren:

- durations;
- easing;
- reveal;
- menu;
- modal/dialog;
- hover transitions.

Keine unnötige Animation.

### ST05.1.9 — Token Guard in CI

Bestehenden Guard nutzen:

`scripts/check-color-tokens.mjs`

Verbindlich:

- pre-commit-Verhalten erhalten;
- CI explizit um Token-/Color-Gate ergänzen, wenn noch nicht vorhanden;
- neue kanonische Farbwerte müssen Guard und Tokenquelle im selben Commit berücksichtigen;
- keine zweite Color-Lint-Implementierung.

## 6.3 Verifikation

Mindestens:

- `npm run check:colors`
- Typecheck
- Lint
- relevante Tests
- Build
- gezielte Kontrastchecks

# 7. PT05.2 — Typografie

## 7.1 Ziel

Eine stabile, selbstgehostete und responsive Typografie für alle späteren Seiten-APs bereitstellen.

## 7.2 Selbstgehostete Inter-Pipeline

Verbindlich:

- Inter bleibt selbstgehostet;
- keine Google Fonts;
- kein externes Font CDN;
- keine User-IP-Weitergabe an Fontprovider;
- lokale Fontdateien / bestehende Buildpipeline.

Bestehende SSR-Font-Preload-Logik nicht unnötig brechen.

## 7.3 H1–H6

Definieren und technisch abbilden:

- klare Hierarchie;
- responsive Größen;
- line-height;
- weight;
- tracking;
- keine Überschriften nur aus visueller Größe ableiten.

H1 darf Hero-stark sein, aber responsive bleiben.

## 7.4 Textstile

Mindestens:

- Body
- Lead
- Small
- Caption
- Label
- Eyebrow, falls kanonisch
- Helper/Error text

## 7.5 Links

Definieren:

- inline link;
- navigation link;
- CTA-like link;
- focus;
- hover;
- visited nur wenn Produktdesign sinnvoll;
- underline/other affordance darf nicht nur Farbe sein.

## 7.6 Lesebreite Longform

Konsolidieren:

- max readable width;
- paragraph spacing;
- headings;
- lists;
- tables;
- captions;
- evidence/longform.

## 7.7 Responsive Typografie

Keine mobile Overflow-Probleme.

Prüfen:

- H1 in allen 10 Sprachen;
- lange deutsche/niederländische/tschechische Begriffe;
- CTA Labels;
- mobile widths.

## 7.8 Fallback-Metriken

Prüfen:

- Inter fallback;
- CLS-Risiko;
- font-display;
- fallback metrics soweit bereits unterstützt;
- SSR/Client Konsistenz.

## 7.9 Verifikation

Mindestens:

- Build;
- SSR smoke;
- local font requests only;
- keine fonts.googleapis.com / fonts.gstatic.com;
- Typecheck;
- visual smoke Desktop/Mobile;
- 10-language long-string sanity.

## 7.10 Akzeptanzkriterien

- [ ] Inter selbstgehostet
- [ ] keine externe Font-CDN-Abhängigkeit
- [ ] H1–H6 Regeln
- [ ] Body/Lead/Caption/Label
- [ ] Links
- [ ] Longform width
- [ ] responsive type
- [ ] fallback metrics
- [ ] SSR/Client konsistent
- [ ] State auf PT05.3

# 8. PT05.3 — Core UI-Komponenten

## 8.1 Ziel

Die Core UI-Komponenten so konsolidieren, dass AP06–AP21 sie zuverlässig wiederverwenden können.

## 8.2 Button / Link

Mindestens:

- primary;
- secondary;
- outline;
- ghost/text, falls erforderlich;
- destructive nur wenn fachlich notwendig;
- sizes;
- disabled;
- loading;
- icon-only;
- external link semantics;
- focus-visible;
- ≥44 px Target, wo anwendbar.

Bestehendes `class-variance-authority`-Pattern bevorzugen, sofern aktuelle Repo-Evidenz dies bestätigt.

## 8.3 Inputs / Textarea / Choice Controls

Mindestens:

- text input;
- email/tel, soweit generisch;
- textarea;
- checkbox;
- radio;
- select, falls Bestandteil des bestehenden Systems.

States:

- default;
- hover;
- focus;
- error;
- disabled;
- readonly, falls nötig;
- required semantics.

## 8.4 FormField Pattern

Verbindlicher Zusammenhang:

- label;
- control;
- description/help;
- required marker;
- error;
- id / aria relationships.

Keine Seitenformularlogik aus AP20/AP22 vorziehen.

## 8.5 Alert / Status

Semantik trennen:

- info;
- success;
- warning;
- error.

Nicht nur Farbe.

Statusfarben mit PT05.1 konsistent.

## 8.6 Card

Konsolidieren:

- generic card primitive;
- interactive card semantics;
- non-interactive card;
- spacing;
- borders/shadows;
- hover nur bei Interaktion;
- keine zehn duplizierten Kartenrezepte.

Spezialisierte fachliche Cards dürfen auf Primitive aufbauen.

## 8.7 Modal / Drawer / Dialog

Mindestens:

- semantic dialog;
- focus handling;
- Escape;
- close button;
- scroll lock;
- backdrop;
- mobile drawer;
- reduced motion;
- keine Interaktionsblockade nach close.

Art-direction-neutrale Patterns aus `redesign/preview` dürfen adaptiert werden.

## 8.8 Loading / Empty / Error

Standardisieren:

- loading;
- skeleton nur wenn sinnvoll;
- empty;
- recoverable error;
- non-recoverable error;
- retry, wo fachlich möglich.

Keine chat-/route-spezifische Businesslogik.

## 8.9 Touch Targets

Wo anwendbar:

≥44×44 CSS px für interaktive Controls.

Insbesondere:

- icon buttons;
- mobile menu controls;
- close buttons;
- pagination;
- small CTA controls.

## 8.10 Tests

Komponententests mindestens für:

- Button;
- FormField;
- Choice Control(s);
- Alert;
- Card;
- Dialog/Drawer;
- Loading/Empty/Error.

Tests aus `redesign/preview` nur als neutrales Pattern übernehmen.

## 8.11 Akzeptanzkriterien

- [ ] Button/Link konsolidiert
- [ ] Inputs/Textarea/Choices
- [ ] FormField Pattern
- [ ] Alert/Status
- [ ] Card
- [ ] Modal/Drawer/Dialog
- [ ] Loading/Empty/Error

# 10. PT05.5 — Motion, Visual Regression und Error States

## 10.1 Ziel

Die Design-System-Baseline gegen Interaktions-, Motion- und visuelle Regressionen absichern.

## 10.2 Reduced Motion

Verbindlich:

`prefers-reduced-motion` respektieren.

Betroffen mindestens:

- reveal;
- page transitions;
- menu;
- modal/dialog/drawer;
- sticky/chapter interactions soweit animiert.

Reduced Motion darf Funktion nicht entfernen.

## 10.3 Transitions

Standardisieren:

- reveal;
- menu open/close;
- modal/drawer;
- hover/focus transitions.

Regeln:

- kurz;
- nicht blockierend;
- nicht für kritische Statusänderung nötig;
- keine künstlichen Delays.

## 10.4 Keine Interaktionsblockade

Prüfen:

- hidden overlays;
- lingering pointer-events;
- scroll lock cleanup;
- focus restoration;
- animation state nach navigation;
- modal close.

## 10.5 Visual-Regression-Baseline

Art-direction-neutrales Pattern aus `redesign/preview` adaptieren.

Baseline-Surfaces mindestens:

- core UI showcase/test route nur falls bestehende Teststrategie es erlaubt;
- Homepage repräsentative Sales-Machine-Fläche;
- Diagnostics/Card Pattern;
- Form components;
- Dialog/Drawer;
- longform/chapter pattern;
- error state.

Keine Test-only öffentliche Produktionsroute erfinden, wenn nicht nötig.

## 10.6 Baseline Screenshots

Deterministisch:

- definierte viewport sizes;
- stabile Fonts;
- Animationen deaktiviert/reduced;
- keine live/zeitabhängigen Inhalte;
- keine Secrets/PII;
- klare Update-Konvention.

## 10.7 Route Error Boundaries

Übernehme art-direction-neutrales technisches Pattern:

- recoverable route/render error;
- fallback surface;
- retry/reload, wo sinnvoll;
- kein Fehler als 404 maskieren;
- Design-System Error State verwenden.

Routingstatus selbst bleibt AP10/Runtime Contract.

## 10.8 Changelog Gate

Für relevante Design-System-Änderungen:

- dokumentierte Change Note;
- keine stillen Token-/Component-Contract-Brüche;
- CI/Guard gemäß bestehender Repository-Konvention.

Wenn noch kein Changelog-System kanonisch existiert, minimalen design-systembezogenen Gate-Mechanismus nutzen, ohne AP27 vollständig vorwegzunehmen.

## 10.9 Akzeptanzkriterien

- [ ] Reduced Motion
- [ ] standardisierte transitions
- [ ] keine animation-blocked interactions
- [ ] visual regression baseline
- [ ] baseline screenshots
- [ ] route error boundary pattern
- [ ] design-system error state
- [ ] changelog gate
- [ ] Tests/Build grün
- [ ] State auf AP05-CLOSURE
