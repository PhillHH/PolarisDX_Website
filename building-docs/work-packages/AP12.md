# 0. Zweck und Rolle von AP12

AP12 baut aus `/diagnostics` den zentralen, verständlichen und conversion-fähigen Einstieg in die diagnostischen Leistungsbereiche von PolarisDX.

Der Hub soll nicht als bloße Liste aus neun Links funktionieren. Er muss Nutzern schnell beantworten:

- Welche diagnostischen Leistungsbereiche bietet PolarisDX?
- Welche Themen sind für meine Praxis / mein Anwendungsfeld relevant?
- Wo liegt der Unterschied zwischen Point-of-Care, erweiterten diagnostischen Leistungen und System-/Integrationsangeboten?
- Welche Service-Seite ist mein sinnvoller nächster Schritt?
- Wie komme ich bei Kauf-/Beratungsinteresse zu „Angebot anfragen“?

AP12 besitzt die Informationsarchitektur und Hub-Präsentation. AP13 besitzt die vollständige fachliche Ausarbeitung der neun Service-Detailseiten.

Der Hub darf daher genug Kontext geben, um die Auswahl verständlich zu machen, aber nicht die Detailseiten duplizieren.

Nutzer müssen innerhalb weniger Sekunden verstehen:

- was PolarisDX unter Diagnostics anbietet

- wie Point-of-Care einzuordnen ist

- aktuelle Service Slugs
- aktuelle Reihenfolge
- vorhandene Kategorien
- vorhandene Teasertexte
- aktuelle interne Links
- Search Coverage
- Homepage Deep Links
- Route Registry Coverage

## 8.3 POC vs. Labor-/erweiterte Diagnostik

Die Seite muss den Unterschied verständlich erklären, ohne eine künstliche harte medizinische Trennung zu erfinden.

Copy-Anforderungen:

- anwenderverständlich
- fachlich vorsichtig
- kein unnötiger Jargon
- keine Abwertung klassischer Labordiagnostik
- keine unbelegten Überlegenheitsclaims
- keine implizite medizinische Garantie

## 8.4 Nutzerorientierte Gruppierung

Gruppierung basiert primär auf:

- Ziel / Use Case
- Fachgebiet
- Versorgungskontext
- Workflow / Anwendung

Nicht nur auf internen Produktnamen oder Testlisten.

## 8.5 Top-Prioritäten

Top-Prioritäten dürfen visuell hervorgehoben werden, wenn dies durch aktuelle Produktstrategie / bestehende Site-Hierarchie gestützt ist.

Keine Priority erfunden, nur weil eine Karte optisch Platz braucht.

Keine Glossary-Plattform bauen.

## 8.7 Service Coverage

Alle neun Families müssen im Hub vorkommen.

Keine Family darf:

- nur über Search erreichbar sein
- nur über direkte URL erreichbar sein
- versehentlich aus Mobile verschwinden
- auf einen Legacy-Pfad zeigen

## 8.8 Hub-vs-Detail Grenze

Hub Teaser beantworten:

- Was ist das Thema?
- Für wen ist es relevant?
- Welchen Nutzen / Use Case adressiert es?

Hub Teaser beantworten nicht vollständig:

- alle Parameter
- vollständige Fachworkflow-Details
- alle FAQs
- tiefe Proof-/Literaturführung

Das gehört AP13.

## 8.9 Datenmodell

Zulässige Felder semantisch z.B.:

- id
- slug
- titleKey
- teaserKey
- category
- specialtyTags
- priority
- icon
- route

Bestehende Architektur bevorzugen.

Keine konkurrierende Service-SSOT.
