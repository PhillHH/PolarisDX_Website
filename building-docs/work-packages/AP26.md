# 0. Zweck

AP26 macht Security zu einem reproduzierbaren Qualitätsvertrag des Relaunches. Es geht nicht darum, möglichst viele Header oder Scanner einzubauen, sondern die tatsächlich vorhandenen Web-, API-, Lead-, Queue-, Secret- und Container-Angriffsflächen so abzusichern, dass der spätere Produktionsbetrieb belastbar, testbar und ohne False-ready-Behauptungen freigegeben werden kann.

AP26 besitzt systemweit insbesondere:

- Security Header und HTTPS-/Origin-Härtung
- CSP-Finalisierung und Legacy-/Chat-Domain-Bereinigung
- API-/Form-Security für alle launchrelevanten Endpunkte
- Payload-/Attachment-Limits und sichere Fehlersemantik
- Origin-/CSRF-/CORS-Risikobewertung passend zur echten Architektur
- Rate Limit, Honeypot/Abuse-Schutz und Idempotenz-Reverification
- Secrets außerhalb Repo und Images
- Least-Privilege- und Environment-Trennung
- PII-/Secret-Redaction in Logs
- Queue-/Retry-/Replay-Sicherheit
- Webhook-Signaturprüfung, falls Rückrufe existieren
- Backup-/Restore-Zugriffsschutz als Security-Grenze
- Dependency-, Secret- und Container-/Image-Scanning
- Preview-/Staging-Isolation ohne produktive Side Effects
- Security-Budgets/Gates in CI, soweit AP26-eigen

AP26 darf keine bestehende Consent-, Accessibility-, Performance-, Routing-, SEO-, Lead- oder Deployment-Wahrheit schwächen, nur um einen Security-Check formal grün zu bekommen.

# 4. Harte AP26-Regeln

- Keine Secrets in Repository, Build-Artefakten, Images, Browser-Bundles oder Logs.
- Keine Secret-Werte in Agentenreports, Handoffs oder CI-Ausgaben wiederholen.
- Ein bereits exponiertes Credential wird nicht als „durch Scan jetzt sicher“ betrachtet; Rotation ist Operator-Arbeit und muss als solche markiert werden.
- Kein `.env`-Commit, kein Copy von produktiven `.env`-Dateien in Images.
- Keine Nutzung von `ARG`/`ENV` für echte Runtime-Secrets, wenn dadurch Image-Layer das Secret enthalten könnten.
- Preview/Staging und Production müssen getrennte Credentials/Endpoints besitzen oder Preview muss Side Effects technisch unterbinden.
- X-Powered-By bleibt entfernt.
- HSTS nur für echte HTTPS-Produktions-/Proxy-Semantik; localhost/dev nicht künstlich unbrauchbar machen.
- Kein HSTS-Preload-Claim ohne separate, bewusste Operator-Entscheidung und Domainprüfung.
- CSP-Allowlist folgt realen Runtime-Abhängigkeiten, nicht Bequemlichkeit.
- Keine unnötigen `*`-Wildcards in CSP.
- `unsafe-eval`/`unsafe-inline` dürfen nicht blind akzeptiert werden; falls technisch noch erforderlich, Rest-Risiko exakt dokumentieren und Enforce-Readiness nicht falsch behaupten.
- Chat-/HiHuman-/Legacy-Provider-Domains dürfen nicht in CSP/Code/Endpoint zurückbleiben, wenn die Funktion entfernt ist.
- GTM/GA4-CSP-Erlaubnis ist keine Erlaubnis für Pre-Consent-Requests; AP23 Network-Gate bleibt unverändert.
- Report-Only nur mit bewusstem Zweck; ohne funktionierenden Report-Empfänger darf kein „Monitoring aktiv“-Claim entstehen.
- Keine API akzeptiert frei manipulierbare Dateisystempfade oder ungebundene Produkt-/Journey-Identifiers.
- Servervalidierung ist autoritativ; Clientvalidierung ist UX, keine Security-Grenze.
- Rate Limits, Honeypot/Abuse-Schutz und Idempotenz dürfen nicht nur clientseitig existieren.
- Fehlerantworten geben keine Stacktraces, Dateipfade, SQL, Secret-Fragmente oder Provider-Interna preis.
- CSRF-/Origin-Schutz wird aus dem echten Auth-/Cookie-/CORS-Modell abgeleitet; keine Cargo-Cult-Token.
- CORS darf nicht breit auf `*` stehen, wenn Credentials oder sensible POST-Endpunkte betroffen sind.
- Attachment-/Payload-Limits müssen vor speicher-/CPU-intensiver Verarbeitung greifen.
- Uploads werden nicht nach Client-Dateinamen oder Content-Type allein vertraut.
- PII wird nur minimal geloggt; Auth-/Token-/Entitlement-Werte werden redigiert.
- Queue-Replay darf keine doppelten externen Side Effects erzeugen.
- Unknown provider result darf nicht blind wiederholt werden, wenn AP22 bereits einen Reconciliation-State vorsieht.
- Webhook-Signaturprüfung ist Pflicht, falls produktive eingehende Provider-Webhooks existieren; wenn keine Webhooks existieren, darf keine Scheinsignaturprüfung erfunden werden.
- Backup-/Restore-Zugriffe sind Teil der Security-Grenze, aber AP28 bleibt Owner von Backup/Recovery-Operations.
- Security-Scanner dürfen keine Dateien löschen oder Lockfiles eigenmächtig aktualisieren.
- Vulnerability-Ausnahmen brauchen Paket, Version, CVE/Advisory, Reachability/Impact, Entscheidung und Review-Termin.
- Container-/Image-Scan muss auf dem tatsächlich gebauten Image laufen, nicht nur auf dem Dockerfile.
- Keine Security-Funktion darf Accessibility-/Consent-/Lead-/Performance-Verträge regressieren.
- Shopify bleibt externer Shop; AP26 baut keinen eigenen Checkout/Payment-Flow. Falls ein historischer Consumer-Inquiry-Endpunkt noch existiert, wird dessen reale Security geprüft oder seine Entfernung nachgewiesen — er wird nicht künstlich wiederbelebt.

# 8. PT26.1 — Security Headers und Security-Baseline

## Ziel

Eine aktuelle Security-Baseline herstellen und die Web-/SSR-/Proxy-Header so härten, dass jeder späterer Security-Delta auf messbarer Wahrheit aufsetzt.

## Scope

- Security-Surface-Inventar und Threat-Matrix
- X-Powered-By entfernt halten
- HSTS-Ownership und Produktionskonfiguration
- Referrer-Policy
- Permissions-Policy
- Frame-Schutz (`frame-ancestors` / X-Frame-Options kompatibel)
- MIME Sniffing / `X-Content-Type-Options`
- HTTPS-only / forwarded proto semantics
- Cache-/No-store-Semantik für sensible Antworten
- Header-E2E auf repräsentativen 200/301/404/API/protected responses
- Initialisierung `building-docs/SECURITY-CONTRACT.md`

## Bounded Discovery

Einmalig erheben:

- welche Security Header heute aus App, API, nginx/Proxy oder CDN kommen
- ob dieselben Header doppelt/widersprüchlich gesetzt werden
- ob `trust proxy`/Forwarded-Header sicher und konsistent verwendet werden
- welche Origin/Host/Proto-Annahmen bestehen
- welche API-/protected Routen andere Cache-/Header-Semantik brauchen
- welche CSP aktuell Report-Only oder Enforced ist
- welche Preview-/Production-Unterschiede real existieren

## HSTS

HSTS ist nur PASS, wenn:

- Produktions-HTTPS eindeutig ist
- Header am finalen Origin/Proxy path gesetzt wird
- kein localhost/dev-HSTS erzwungen wird
- Subdomain-Einbeziehung nicht blind gesetzt wird
- Preload nicht behauptet wird, sofern nicht bewusst separat entschieden

Falls Live-Origin vor Relaunch noch nicht umgestellt ist, darf AP26 die produktionsreife Konfiguration + production-like Evidence als PASS führen, muss aber Live-Aktivierung als AP31 Operator Check markieren.

## Header-Matrix

Mindestens prüfen: HTML 200, 301, 404, API 2xx, API 4xx, API 429, protected asset success, protected asset reject.

## Akzeptanz

- Header-Ownership dokumentiert
- keine widersprüchlichen Header
- X-Powered-By absent
- HTTPS/HSTS truth-safe
- Referrer/Permissions/Frame/MIME Policies sinnvoll
- sensible Routen mit passender Cache-Semantik
- Header-E2E grün
- SECURITY-CONTRACT initialisiert

## Focused Tests

- Header snapshot/matrix against production-like server
- HTTP→HTTPS semantics where owned by repo
- forwarded-proto handling
- 200/301/404 parity
- API 4xx/429 no internals
- protected response headers

# 10. PT26.3 — API- und Formular-Security

## Ziel

Alle launchrelevanten API-/Form-Endpunkte serverseitig gegen ungültige Eingaben, Missbrauch, übergroße Payloads, Replay und Informationsleckage härten.

## Endpoint-Inventar

Aus Repository Truth ermitteln. Typische Kandidaten, sofern noch aktiv: contact, support, epigenetics inquiry, ROI/report request, content_download, lead_magnet/protected asset, consumer inquiry/order legacy path, weitere Shared-Lead-Endpunkte. Entfernte oder Shopify-supersedete Endpunkte nicht künstlich wiederherstellen.

## Pro Endpoint prüfen

- HTTP method / content type
- serverseitiges Input-Schema
- unknown-field behavior
- Längen-/Formatgrenzen
- Payload limit
- Attachment limit
- Rate limit
- Honeypot/equivalent abuse control
- Processing consent
- Marketing consent separation
- Idempotency/replay semantics
- Origin/CORS/CSRF risk
- error contract
- PII/log behavior

## Payload / Attachment Security

- Request size limit before expensive parsing where feasible
- per-field bounds
- file count and total bytes
- filename normalization only for display; storage path server-owned
- MIME/extension/content checks appropriate to actual accepted types
- no path traversal
- temporary/storage failure truth-safe

## CSRF / Origin / CORS

Bewertung basiert auf realer Architektur:

- Cookie-authenticated state-changing endpoint → echte CSRF-Grenze nötig
- unauthenticated lead form → CSRF-Token ist nicht automatisch der richtige Control; Origin/Host, rate limit, honeypot, idempotency und abuse semantics bewerten
- CORS nur benötigte Origins/Methods/Headers
- keine credentials+wildcard Kombination

## Failure Semantics

- keine Stacktraces
- keine Dateipfade
- keine SQL/DB-Details
- keine Provider-Secrets
- keine vollständigen Request Bodies
- keine false-success response bei persist/retry failure

## Akzeptanz

- jede aktive API hat explizites serverseitiges Schema
- Rate limits auf allen extern erreichbaren write endpoints oder begründete Ausnahme
- Payload-/Attachment-Limits real
- abuse controls real
- idempotency where state/side-effect requires it
- Origin/CORS/CSRF risk documented and controlled
- error responses without internals
- no PII/secret leakage in logs

## Focused Negative Tests

- oversized JSON/body
- unknown fields
- invalid enum/product/asset/journey
- invalid locale
- missing processing consent
- honeypot
- rate limit
- duplicate idempotency key with same body
- same key different body
- malformed content type
- attachment too large
- path traversal filename
- host/origin mismatch according to chosen policy
- provider error does not leak internals

# 11. PT26.4 — CRM, Queue, Secrets und Integration Security

## Ziel

Die Shared Lead Foundation und externen Integrationsgrenzen so härten, dass Credentials, PII, Replay und Environment-Separation produktionsreif behandelt werden.

## Secrets

- Repo/current tree auf Secret-Muster prüfen
- Build context / Docker history / image env prüfen
- Browser bundle auf provider/API secrets prüfen
- `.env.example` nur Namen/Platzhalter
- Runtime Secret Injection statt Image Baking
- Rotation-Runbook für exponierte Credentials dokumentieren
- keine Secret-Werte in Reports übernehmen

## Environment Separation

- Preview/Staging keine produktiven CRM/Mail Side Effects
- separate credentials/endpoints oder technische hard-disable Strategie
- Production-only integrations nicht durch Preview erreichbar
- DRY_RUN/Sandbox semantics truth-safe

## Least Privilege

Für jede externe Integration dokumentieren: benötigte Aktion, Credential-Typ, minimale Rechte, Environment, Rotation Owner. Keine Rechte erfinden; wenn Providerrechte extern nicht verifizierbar sind, Operator Check statt Fake PASS.

## Queue / Replay

- persist-before-handoff erhalten
- dedupe/idempotency erhalten
- worker replay ohne duplicate side effect
- retry budget/backoff existiert oder Owner dokumentiert
- poison job/dead-letter Verhalten ehrlich
- unknown provider result nicht blind wiederholen
- PII in queue payload minimal und logs redigiert

## Webhooks

Nur wenn produktive Rückrufe existieren:

- Signatur/HMAC anhand Raw Body prüfen
- Timestamp/replay window falls Provider vorsieht
- constant-time compare where applicable
- unknown event safe
- idempotent event processing

Keine Webhooks vorhanden → `NOT_APPLICABLE`, nicht künstlich einen Endpoint bauen.

## Backup-Zugriff

AP26 prüft, dass DB/backup/volume nicht öffentlich oder in Webroot liegt und dass Credentials/Permissions sauber geplant sind. Restore/RPO/RTO bleiben AP28.

## Akzeptanz

- 0 Secrets in tracked files/current built artifacts
- 0 Secrets in image layers/env where scan can prove it
- Preview/Production credential separation
- Least privilege documented or explicit external blocker
- PII/token log redaction
- Queue replay/dedupe security green
- Webhook signature real or N/A
- backup boundary not public

## Focused Tests

- secret scan on working tree + relevant tracked history/window without rewriting history

# 12. PT26.5 — Security QA und CI-Gates

## Ziel

## Scope

- Dependency Audit für Root und Server
- Secret Scan
- Header/CSP E2E
- API Rate-Limit-/Abuse-/Payload-Tests
- Container-/Image-Scan
- Image secret/history inspection
- Preview side-effect isolation
- No-chat/legacy-provider guard
- Security test scripts / CI steps
- Vulnerability exception process
- breiter Integration-/Regression-Lauf

## Dependency Audit

Muss Root und `server/` abdecken. Policy:

- direkte/runtime Dependencies strenger als reine dev-only findings bewerten
- Severity allein reicht nicht; Reachability/Deployment-Kontext dokumentieren
- kein blindes `npm audit fix --force`
- Lockfile nur gezielt ändern, mit Regressionstest
- unfixable finding → Risk Acceptance mit Review-Termin, nicht verschweigen

## Secret Scan

Mindestens: tracked current tree, diffs/branch range passend zum Projekt, Docker build context, built artifacts. Keine Secret-Werte in CI-Ausgabe spiegeln.

## Container/Image Scan

Auf tatsächlich gebautem Frontend- und Backend-Image. Prüfen: OS packages, Node dependencies soweit Scanner unterstützt, image user, env, exposed ports, unnecessary tools, critical/high findings. AP28 bleibt Owner der finalen Betriebsarchitektur.

- dependency audit
- secret scan
- security contract tests
- image scan sofern CI Image Build praktikabel und Ownership mit AP28/AP27 koordiniert
  Keine bestehende AP24/AP25-Gate-Definition überschreiben.

## Preview Side Effects

Preview-Test muss beweisen: keine produktiven CRM-/Mail-/Webhook-/sonstigen Side Effects. Wenn ein Provider nicht sandboxfähig ist, muss die Integration in Preview technisch blockiert sein.

- Secret scan PASS oder explizite rotierte/historische Finding-Dokumentation
- Header/CSP tests PASS

# 15. Risikoregister

## R26-01 — Secret im Repo/Image

**Risiko:** Provider-Credential landet in Git, Build-Context oder Image-Layer.

**Mitigation:** Secret Scan + Runtime Injection + Image History Scan + Rotation-Runbook.

## R26-02 — CSP zu breit

**Risiko:** Wildcards/unsafe directives reduzieren Schutz auf Papierwert.

**Mitigation:** Source-by-source Allowlist, Browser-E2E, dokumentierte Rest-Risiken.

## R26-03 — CSP zu streng

**Risiko:** Enforce-Policy bricht Consent, Formulare, Fonts oder Kernseiten.

**Mitigation:** Report-Only/production-like Browserlauf vor Enforce.

## R26-04 — HSTS Fehlkonfiguration

**Risiko:** Subdomains/dev werden ungewollt gebrickt.

**Mitigation:** Owner/Domain-Scope prüfen; kein blindes includeSubDomains/preload.

## R26-05 — API Abuse

**Risiko:** Form-/Upload-Endpunkte erlauben Spam/DoS/oversized payloads.

**Mitigation:** Server limits + rate limit + honeypot + negative tests.

## R26-06 — Info Leak

**Risiko:** Stacktrace/DB/Providerdetails gelangen in 4xx/5xx oder Logs.

**Mitigation:** Error contract + log redaction tests.

## R26-07 — Replay Doppelwirkung

**Risiko:** Queue/API retry erzeugt doppelte CRM-/Mail-Side-Effects.

**Mitigation:** Durable idempotency + replay tests + unknown-result state.

## R26-08 — Preview trifft Produktion

**Risiko:** Preview nutzt echte CRM/Mail/Production-Credentials.

**Mitigation:** Environment separation + hard-disable/sandbox + side-effect tests.

## R26-09 — Supply-Chain Finding ignoriert

**Risiko:** Audit wird nur „grün gemacht“, ohne Reachability zu bewerten.

**Mitigation:** Triage-Template + Risk Acceptance + Review-Termin.

## R26-10 — Scanner scannt falsches Artefakt

**Risiko:** Dockerfile/lockfile ist sauber, produktives Image aber nicht.

**Mitigation:** tatsächliche Images bauen und scannen.

## R26-11 — Legacy Provider bleibt erlaubt

**Risiko:** Entfernte Chat-/Legacy-Domains bleiben in CSP/Code und vergrößern Angriffsfläche.

**Mitigation:** No-legacy guard + CSP diff.

## R26-12 — Security bricht andere Verträge

**Risiko:** Header/CSP/limits regressieren Consent, A11y, Performance oder Lead-Flows.

**Mitigation:** Cross-regression gate in PT26.5 und Closure.
