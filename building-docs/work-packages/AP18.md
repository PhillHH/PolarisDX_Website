# 8. Date-only vs. Datetime Contract

## 8.1 Date-only

Wenn Eventdaten nur `YYYY-MM-DD` enthalten:
Diese Werte repräsentieren **lokale Kalendertage**, keine UTC-Mitternachtszeitpunkte.

Sie dürfen nicht durch:
`new Date("YYYY-MM-DD")`
mit impliziter UTC-Semantik zu Off-by-one-Fehlern führen.

## 8.2 Datetime

Wenn echte Uhrzeiten existieren:

- Zeitzone explizit oder aus belastbarem Contract
- keine Browser-Local-Time-Abhängigkeit
- SSR und Client müssen gleich klassifizieren

## 8.3 All-Day

Date-only Kalenderexport:
All-Day Event.

Keine Uhrzeit erfinden.

# 9. Status Contract

Jedes aktuelle Event lässt sich deterministisch klassifizieren:

- `upcoming`
- `ongoing`
- `past`

oder semantisch gleichwertige vorhandene Begriffe.

Regel:

## eintägig

- vor Eventtag: upcoming
- am Eventtag: ongoing/current
- nach Eventtag: past

## mehrtägig

- vor Starttag: upcoming
- Starttag bis einschließlich Endtag: ongoing/current
- nach Endtag: past

Vergleich in korrekter Event-Date-/Timezone-Semantik.

# 29. AP18 Invarianten

## EVT-01 — Predecessor Integrity

AP17 muss COMPLETE / Closure PASS sein, bevor AP18 produktiv startet.

## EVT-02 — Ten Locales

Events UI und lokalisierbare Eventtexte unterstützen exakt zehn Projektsprachen: de, en, pl, fr, it, es, pt, da, nl, cs.

## EVT-03 — Default Locale

Default Locale und x-default bleiben de.

## EVT-04 — Stable Event IDs

Bestehende Event-IDs bleiben stabil, weil sie zugleich i18n-Schlüssel sind; Änderungen erfolgen nur als bewusste Migration über alle zehn Locales.

## EVT-05 — Single Event Identity

Jedes Event besitzt genau eine stabile interne Identität; Upcoming-/Past-Darstellung erzeugt keine Duplikate.

## EVT-06 — Start Date Truth

Startdatum stammt ausschließlich aus realer Eventdatenquelle und wird nicht aus UI-Text zurückgeparst.

## EVT-07 — End Date Truth

Enddatum ist optional, aber wenn vorhanden real und nicht vor Startdatum.

## EVT-08 — Date-only Semantics

Date-only Events werden als Kalendertage behandelt und nicht durch UTC-Mitternacht um einen Tag verschoben.

## EVT-09 — Timezone Explicitness

Zeit-/Zeitzonenlogik ist deterministisch; für Events mit Uhrzeit muss eine explizite Event-Zeitzone oder gleichwertige belastbare Semantik vorliegen.

## EVT-10 — Ongoing Event Not Past

Ein mehrtägiges Event bleibt bis zum Ende seines letzten realen Eventtages aktuell/kommend und wird nicht zu früh archiviert.

## EVT-11 — Past Transition Automatic

Nach Ablauf verschiebt sich ein Event automatisch in den Rückblick; keine manuelle Doppelpflege desselben Events.

## EVT-12 — Injected Clock

Sortier-/Statuslogik ist mit injizierbarer/fixierbarer Zeit testbar und hängt nicht untestbar direkt von zufälligem `Date.now()` ab.

## EVT-13 — Chronological Upcoming

Kommende/laufende Events sind deterministisch chronologisch sortiert.

## EVT-14 — Past Ordering

Rückblick ist deterministisch absteigend nach realem Eventende/Start sortiert.

## EVT-15 — Highlight Real

Highlight verweist ausschließlich auf ein reales Event und erzeugt keinen Phantomtermin.

## EVT-16 — Highlight Eligibility

Ein abgelaufenes Event darf nicht weiterhin als Upcoming-Highlight dargestellt werden.

## EVT-17 — Partner Truth

Partnernamen werden nur aus realen Eventdaten ausgegeben und nicht übersetzt oder erfunden.

## EVT-18 — Location Truth

Ortsnamen bleiben reale Ortsnamen; keine künstliche Übersetzung oder Geocoding-Erfindung.

## EVT-19 — External Link Truth

Externe Eventlinks existieren nur, wenn real hinterlegt; kein generischer Fake-CTA.

## EVT-20 — External Link Safety

Externe Links verwenden sichere Browser-Semantik (`rel`/Target) und keine unsicheren opener-Flows.

## EVT-21 — Calendar Link Conditional

Kalenderlink wird nur angeboten, wenn Datum/Zeitzoneninformationen für einen korrekten Kalender-Eintrag ausreichen.

## EVT-22 — Calendar Data Truth

# 30. Risikoregister

## R18-01 — Events wechseln wegen UTC-Mitternacht einen Tag zu früh in den Rückblick

**Risiko:** Events wechseln wegen UTC-Mitternacht einen Tag zu früh in den Rückblick.

**Mitigation:** Date-only Semantik als Kalendertage, eventbezogene Zeitzone und fixierte Boundary-Tests.

## R18-02 — Mehrtagesevent wird nach Starttag archiviert

**Risiko:** Mehrtagesevent wird nach Starttag archiviert.

**Mitigation:** Status auf Enddatum bzw. Startdatum bei eintägigem Event basieren; laufende Phase testen.

## R18-03 — Stabile ID wird umbenannt und bricht x10 i18n

**Risiko:** Stabile ID wird umbenannt und bricht x10 i18n.

**Mitigation:** ID-Migrationsgate über Datenquelle + zehn Locale-Dateien; Standard: IDs unverändert.

## R18-04 — Highlight zeigt abgelaufenes oder fehlendes Event

**Risiko:** Highlight zeigt abgelaufenes oder fehlendes Event.

**Mitigation:** Eligibility-/Existenzguard; Highlight nur aus aktuellem Eventset.

## R18-05 — Automatisch archiviertes Event erscheint zusätzlich statisch im Rückblick

**Risiko:** Automatisch archiviertes Event erscheint zusätzlich statisch im Rückblick.

**Mitigation:** Dedup über stabile ID und eindeutige Merge-Regel.

## R18-06 — Kalenderlink erfindet Uhrzeit/Zeitzone

**Risiko:** Kalenderlink erfindet Uhrzeit/Zeitzone.

**Mitigation:** Kalender nur bei ausreichender Datenqualität; date-only als All-Day Event.

## R18-07 — Event Schema wird trotz unvollständiger Daten zu aggressiv erzeugt

**Risiko:** Event Schema wird trotz unvollständiger Daten zu aggressiv erzeugt.

**Mitigation:** Schema optional und nur bei required-field-/visible-truth-Prüfung.

## R18-08 — Outbound Tracking sendet pre-consent

**Risiko:** Outbound Tracking sendet pre-consent.

**Mitigation:** bestehende consent-aware Tracking-Fassade + Network-Gate.

## R18-09 — Externe Partner-/Eventlinks werden zu Sicherheits-/Trackingproblem

**Risiko:** Externe Partner-/Eventlinks werden zu Sicherheits-/Trackingproblem.

**Mitigation:** safe rel/target, keine Provider-SDKs, Tracking nur consented.

## R18-10 — x10 wird durch Übersetzung von Eigennamen oder Fallback verfälscht

**Risiko:** x10 wird durch Übersetzung von Eigennamen oder Fallback verfälscht.

**Mitigation:** Partner/Ort als reale Eigennamen; lokalisiert werden nur UI/Eventcopy.

## R18-11 — Tests sind zeitabhängig und flakey

**Risiko:** Tests sind zeitabhängig und flakey.

**Mitigation:** Clock Injection/Fake Timer und feste Boundary-Testdaten.

## R18-12 — AP18 wird unnötig zu Event-CMS/Detailseitenplattform aufgebläht

**Risiko:** AP18 wird unnötig zu Event-CMS/Detailseitenplattform aufgebläht.

**Mitigation:** Master-Scope auf `/events` + Datenmodell/Upcoming/Past/SEO/Tracking begrenzen; spätere Systeme nicht vorziehen.
